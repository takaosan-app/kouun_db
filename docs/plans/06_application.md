# 開発計画書 06：後半・アプリ構築編

版：v0.12／更新日：2026-09-21  
到達目標：PCとスマホから、農地にひも付く気象履歴と作業記録を簡単に確認できる。

## 1. 製品の考え方

農家自身が判断できるように、気象の実績と比較結果を分かりやすく見せる。別会話「気象データの農業活用」で検討した、農地ピン、複数観測所、開花・満開などの基準日、作業記録を反映する。

初期は作物共通の画面を作る。水稲、みかん、イチゴなどを個別に作り込む前に、本人と身近な農家の試用で必要な情報を確認する。観測所の外気データをハウス内の値と混同しない。

FlutterはWeb・iOS・Androidへの展開に対応しているが、地図・位置情報・通知・ファイル操作は各環境で検証する。[Flutter公式](https://docs.flutter.dev/platform-integration/web)、[Supabase Flutter](https://supabase.com/docs/reference/dart/introduction)

サンプル農地は静岡県藤枝市稲川。正確なピンはユーザーが確認する。観測所候補は静岡・静岡空港・高根山と、提供期間確認対象の島田。項目がない場合は「未観測／提供対象外」、期間外は「対象期間外」として、欠測と区別する。

### 2.1 初期対象地域を静岡県と周辺県に限定する

収集と開発は全国を対象に継続する。アプリの初期版だけを、静岡県と静岡県に接する神奈川・山梨・長野・愛知の5県に限定する。利用者も配信する観測所もこの範囲とする。

単県ではなく接する県までを含めるのは、圃場の近隣観測所が県境を越えることがあるためである。静岡県の圃場でも、要素によっては山梨や長野の観測所が最寄りになる。

| 県 | 観測所 |
|---|---:|
| 長野 | 45 |
| 静岡 | 31 |
| 愛知 | 20 |
| 山梨 | 14 |
| 神奈川 | 11 |
| 合計（重複を除く） | **120** |

全国1,286観測所の約1割にあたる。

範囲を限定する第一の理由は、初期の試用者へ聞き取りできる範囲に利用者を絞ることである。アプリ向けDBの容量も理由の一つだが、この規模では制約にならない。

自宅DBの実測から、1観測所あたりの容量は年でL1が0.044MB、L2が0.091MB、公式平年値が0.051MB（期間によらず固定）である。L1は直近18か月、L2はlookback最長10年に当年を加えた11年分を保持する。

| 範囲 | L1（18か月） | L2（11年） | 平年値 | 合計 |
|---|---:|---:|---:|---:|
| 5県120観測所 | 8MB | 120MB | 6MB | **134MB** |
| 全国1,286観測所 | 85MB | 1,287MB | 66MB | 約1.4GB |

5県であれば無料枠500MBに対して余裕がある。全国へ広げるとL2だけで1.3GBとなり収まらない。配信範囲は「観測所数 × 年数」で決まるため、対象地域を広げる際は容量を再計算する。実際の容量は同期方式の決定時に実測する。

なお現時点のL1・L2は2020年以降しか構築していない。11年分がそろうのは過去データの補完が2016年まで進んだ後である。

対象地域の拡大は、利用状況と費用を確認してから段階的に判断する。自宅サーバーへ全国・全期間を保持しているため、配信範囲の変更にデータの再収集は伴わない。

### 2.2 オフライン時の動作

圃場は山間にあることがあり、通信できない場所で作業しながら記録することがある。日誌を主入力とする方針（[04_cultivation_state.md](04_cultivation_state.md)10章）を採る以上、圏外で何も記録できない状態は避ける。

「オフラインでは何もできない」より「多少はできる」とした方が、利用者が記録を始める敷居が下がる。完全なオフライン編集までは実装せず、記録できることだけを保証する。

初期版に含める範囲は次のとおり。

| 操作 | 初期版 | 備考 |
|---|---|---|
| 日誌・栽培イベントの新規登録 | **含む** | 端末へ保存し、通信回復後に送信する |
| 現在状態・注意事項の表示 | **含む** | 取得済みのキャッシュを表示する |
| 直近の観測値の表示 | **含む** | 常時保持する範囲に限る |
| 記録の編集・訂正・取消 | 含まない | 通信回復後に行う |
| 保持範囲を超える過去データの閲覧 | 含まない | 通信時に取得する |
| 複数端末で同じ圃場を同時編集した際の調停 | 含まない | 必要性を確認してから追加する |

未送信キューが成立するのは、主キーをUUIDとし端末側で採番するためである。同じUUIDの行が重複して届いた場合は無視すればよく、競合解決の仕組みを要しない。再送しても結果が変わらない。

同期時に発生しうる日付の衝突（同じ栽培案件・同じ日付の既存イベント）は、特別な同期専用の処理を作らず、通常入力・backdate入力と同じ確認画面（[04_cultivation_state.md](04_cultivation_state.md)7.2）で扱う。オフラインは「保存に失敗したらローカルに残して後で再送する」という一般的な耐障害動作として実装し、専用のオフラインモードを作らない。

端末が常時保持するのは、参照観測所のマスタ、公式平年値、栽培案件の基準日前日のL2行、直近90日のL1・L2とする。圃場あたり約100KBで、オフラインでの状態表示と記録に足りる。

この構成は、後から編集・訂正のオフライン対応を追加する際の土台になる。作り直しにはならない。

### 2.3 外部システム・サービス構成

現時点の案は次のとおり。いずれも確定ではなく、費用・無料枠・制約の確認後に見直す。

```text
自宅サーバー（常駐・systemd timer・Python）
  L0 原本・詳細DB、L1・L2の生成、収集・分析バッチ
  全国・全期間を保持する
        │
        │ 配信範囲のみ同期（L1は直近18か月、L2は直近11年、公式平年値）
        ↓
Supabase（東京リージョン）
  アプリ向けDB（配信分のL1・L2、利用者、圃場、栽培案件、イベント、L3結果）
  認証、RLS（user_id = auth.uid()）
  PostgresのRPC関数（検証・多段書き込み）
  Edge Function（TypeScript・標高取得など短時間で終わる処理）
        ▲│
GCP（Cloud Run Jobs + Cloud Scheduler・Python）─┘
  日次でSupabaseへライブ接続し、L2・状態・日誌からrisk_resultを計算して書き込む
  自宅サーバーの稼働状態に依存しない（自宅停止時もL2は多少古いまま計算を続けられる）
        │
Cloudflare
  日誌画像の保存。DBには画像を置かず、オブジェクトキー等を保存する
        │
        ↓
Flutter（PCブラウザ／Android／iOS）
  Supabaseクライアントで直接接続。常時稼働の自前APIは経由しない
```

自宅サーバーが停止してもアプリは動作し、当日の結果が更新されないだけの状態にする。同期は冪等とし、停止した日は翌日にまとめて再実行できる形とする。GCPのL3日次バッチは自宅サーバーとは独立して動くため、自宅停止の影響はL2の鮮度低下にとどまり、risk_resultの更新自体は止まらない。

自宅サーバーへ外部から直接接続させる構成は採らない。アプリからの参照先はアプリ向けDBに限る。常時稼働のバックエンドAPIは持たない。

### 2.4 検証・多段書き込みと軽量な同期処理の置き場所

Flutterから見て、Supabase以外に呼び出す先が2種類ある。

| 置き場所 | 実行環境 | 用途 | 例 |
|---|---|---|---|
| PostgresのRPC関数 | Supabase内蔵（SQL/PLpgSQL） | データ整合性に直結する検証、複数テーブルへの一括書き込み | 04編7章の同日衝突・未来日の確認、栽培案件作成と初回イベントの同時登録 |
| Edge Function | Supabase内蔵（TypeScript／Deno） | Flutterの操作に応じて即座に動く軽い処理 | 圃場登録時の国土地理院・標高API呼び出し（4.1） |

検証規則をRPC関数に集約することで、Web・Android・iPhoneのどの画面から呼んでも同じ規則がかかる。Edge Functionは実行時間に上限があるため、時間の読めない処理（L3の日次バッチ等）には使わず、GCPのCloud Run Jobsに置く。

利用者が増えてアプリの複数バージョンが同時に使われる段階になったら、スキーマ変更が旧バージョンのアプリを壊さないよう、薄いAPI層の追加を検討する。初期版では不要と判断する。

## 3. 最初に完成させる利用の流れ

```text
農地名と位置を登録
 → 要素ごとに参照観測所を選ぶ（降水量・気温・日照）
 → 最新の利用可能な観測実績と、７日・30日の集計を見る
 → 過去年や近隣観測所との差を確認
 → 作業メモ・開花日などを登録
 → 基準日からの積算を確認
```

日別データだけの段階では「現在の気温」や「今日の確定雨量」は表示しない。「最新の実績：○月○日」「データ更新：○時」のように、観測対象と更新を区別する。数時間先予報は導入するまで機能対象外として扱う。

| 画面 | 主な表示・操作 | 初期の完了条件 |

| 観測所選択 | 要素別に候補３地点。距離、標高差、実測／推計、欠測率 | 降水量・気温・日照それぞれで参照地点を確定できる |
| 農地ダッシュボード | 気温・雨量・日照等、期間集計、基準日集計 | 出典・対象期間・品質を確認可能 |
| 気象履歴 | 日別グラフ・表、期間変更、前年比較 | 値がない箇所をゼロで描かない |
| 観測所比較 | 複数地点の値、差、異常値候補の理由 | 農地の実測と誤解しない表示 |
| 記録 | 作業メモ、作物・品種、播種・開花・満開・収穫等 | 日付の登録・修正・削除ができる |

住所・地番から必ず位置が得られるとは仮定しない。検索結果をユーザーが地図上で確認し、修正したピンを保存する。所在地が不明なまま自動確定しない。

### 4.1 圃場登録時の観測所選択

圃場ごとに単一の参照観測所を持つ設計は採らない。対象5県120観測所のうち、降水量は全120地点が観測するが、気温は76地点（63%）、日照は73地点（61%）しかない。最寄りが雨量専用の地点である場合、気温は別の地点を参照することになる。

要素ごとに候補を3地点ずつ提示し、利用者に選んでもらう。

```text
圃場のピンを置く
  ↓ 要素ごとに観測能力で絞り、候補を3地点ずつ提示

降水量   ☑ 島田 6.2km 標高差 -45m
         ☑ 金谷 11.0km 標高差 +12m
         ☑ 川根本町 18.0km 標高差 +95m     → 3地点とも使う

気温     ◉ 島田 6.2km 標高差 -45m
         ○ 静岡 22.0km 標高差 -38m
         ○ 高根山 11.5km 標高差 +370m      → 1地点を選ぶ

日照     ◉ 静岡 22.0km 標高差 -38m
         ○ ...                             → 1地点を選ぶ
```

降水量だけは3地点すべてを使う。見逃し（観測所で降雨なし、圃場で降っていた）を避けるためで、根拠は[03_data_analysis.md](03_data_analysis.md)10.3にある。気温と日照は主参照1地点とし、比較地点は任意で追加できる。

距離と標高差を必ず併記する。地形を機械判定しないため、「近いが山の上の地点」を利用者が避けられるようにする。上の例では高根山が距離では2番目だが標高差370mあり、選ばれにくいことが一目で分かる。

既定では先頭の地点を選択済みにしておき、そのまま進むこともできるようにする。

圃場の標高は、ピン確定時に国土地理院の標高APIから1回だけ取得する。圃場あたり1回の呼び出しで足りる。取得できない場合は標高差を「不明」と表示し、距離だけで選んでもらう。

風速と湿度は初期版では参照観測所の選択対象に含めない。風速は地形の影響が大きく、距離でも標高差でも代替しにくいうえ、ハウスや防風林のある圃場と観測条件が異なる。L2には累積値を蓄積し続けるため、必要になった時点で追加できる。

### 4.2 圃場カードと日誌入力の構想

圃場ごとに現在状態と注意事項をカード表示する。

```text
ハウスA
紅ほっぺ｜開花期（確認済み）
参照：島田観測所（6.2km・標高差 -45m）
注意事項：直近の気象条件に基づくリスク概要
[今日の記録]

ハウスB
きらぴ香｜本圃・定植後12日
参照：島田観測所（6.2km・標高差 -45m）
開花時期の推定情報
[今日の記録] [開花した] [まだ]
```

入力画面は現在状態に必要な項目だけを段階的に表示する。詳細な温度処理条件や研究用途の
入力は折りたたみ、通常利用では見せすぎない。

日誌入力は1画面で完結させる。

```text
9月19日

天気   [晴] [曇] [雨] [雪]      ← 複数選択
雨     地面が濡れましたか        ← 雨を選んだ場合のみ

メモ（任意）
[                              ]

[保存]
```

最寄り観測所が雨量のみの場合は、気温に別の観測所を指定できる。項目ごとの出典を明示し、複数観測所の値を１地点の実測のように合成しない。履歴上の参照変更は有効日付きで管理する。

## 5. 気象データの表示方針

### 5.1 参照条件を注記ではなく本文として表示する

免責的な注記は読まれないか、信頼を損なう。事実として観測条件を提示する。

```text
✕ ※本データはアメダス観測所の値であり、圃場の実際の値とは異なる場合があります

◯ 参照：島田観測所（6.2km・標高差 -45m）
   気温 日平均 24.5℃（平年比 +1.8℃）
   降水 9/15-17 計28mm
```

距離と標高差が示されていれば、農家は自分の圃場との差を自分で補正できる。多くの農家は
予報と自分の圃場の気温差について感覚を持っているため、この情報が判断材料になる。

気温・降水・日照を同じ形式で表示し、要素ごとに注記の有無を変えない。

### 5.2 気温オフセットは入力させない

圃場と観測所の気温差を利用者に入力させる案は採用しない。

- 入力値が積算温度に反映され、判定を静かに変える
- 判定がずれた際、閾値の問題か入力値の問題か切り分けられなくなる
- 距離と標高差を表示していれば、利用者の頭の中で補正される

将来、実績イベントが蓄積すれば逆算できる。

```text
出穂開始（実績）9/8
積算温度からの推定  9/14
→ この圃場は6日早い
```

品種の係数と圃場のオフセットが混在するため厳密な分離はできないが、同一圃場の翌年以降の
推定には利用できる。

補正できない情報のみを利用者に尋ねる。降水がそれにあたる。

## 6. 通知設計

### 6.1 データ更新時刻の制約

メッシュ農業気象データの更新は1日1回・8時頃、金曜は26日先までの予測計算のため
12時半頃となる。農家の活動開始は5〜6時であり、更新を待つと通知が9時以降になる。

- 前日夜に、予報値を含めて翌朝分の通知を作成する。26日先まで予報があるため、
  前日の確定観測が1日遅れても判定はほぼ変わらない
- 確定値が必要な表示（積算温度の実績等）は1日遅れを許容し、基準日を明示する
- 週次サマリを出す場合、金曜は木曜までのデータになるため月曜朝に寄せる

### 6.2 通知疲れの回避

- 同一リスクの再通知は間隔を空け、段階が上がった場合のみ再通知する
- 前広な判定はアプリ内表示に留め、プッシュは確度の高いものに限る（[03_data_analysis.md](03_data_analysis.md)10.2）

### 6.3 無料層との対応

無料層は事後通知とする方針のため、降水依存のルールと相性がよい。事後であれば
「観測所で降雨があった」という確定事実のみで発報でき、前広にする必要も、利用者へ
確認する必要もない。

前広な事前警告と圃場記録の利用は有料層の機能とする。

## 7. PC・スマホの操作設計

PCでは農地一覧と詳細を並べ、表や比較を見やすくする。スマホでは１画面１目的を基本にし、農地一覧→詳細→記録の短い動線にする。スマホの画面を単に横に引き伸ばしたPC版にはしない。

文字の拡大、十分な操作領域、色だけに頼らない品質表示を採用する。グラフには値を読める表または詳細を付ける。単位と期間を常に表示する。

開花日は本人が入力し、ワンタップの「今日、開花を確認」と後からの日付修正を用意する。未入力でも他の機能は利用できる。基準日を変更した場合は「再計算中」を示し、以前の結果を新しい日付の結果として見せない。

通信不能時は最終取得時刻を明示してキャッシュを表示する。保存に失敗した作業メモを「保存済み」にしない。端末への一時下書きと再送を追加する場合は、重複・競合処理を別途設計する。

前半・中盤は自宅サーバーのDocker Compose上で動作する。APIも同じサーバーに置く場合は独立したサービスとして追加するが、外部公開先はP0で検討する。Flutterの画面やスマホアプリ自体を自宅サーバー内で実行する意味ではない。

## 8. Supabaseとの境界

常時稼働の自前APIを持たない（2.4）ため、画面に必要な範囲だけ返す工夫はAPI設計ではなく、Supabase側の仕組みで行う。

| 目的 | 手段 |
|---|---|
| 自分がアクセス可能な農地一覧・登録・変更 | `field`テーブルへ直接クエリ。RLSが利用者の行だけに絞る |
| 座標・半径・項目で観測所候補を検索 | `weather_station`・`station_element_capability`への直接クエリ、またはPostgresの関数 |
| 観測所・項目・期間で観測実績を取得 | `station_daily_weather`・`station_daily_weather_feature`への直接クエリ |
| 期間・基準日集計と比較結果 | `risk_result`、および`cultivation_state`ビューへの直接クエリ |
| 作業メモ・基準日イベントの管理 | `cultivation_event`への直接クエリ、検証を伴う登録はRPC関数経由（2.4） |
| 管理者向け収集状況 | 自宅サーバー側のViewer（05編）で確認する。アプリの対象外 |

対象期間・件数の上限はクエリ側（`limit`・ページネーション）で設ける。大量取得が必要になった場合はPostgresの関数に寄せ、分割・集計をDB側で行う。分析中・データ不足・提供対象外の区別は、値をnullにし理由となる列（有効件数・欠測フラグ等）を併せて返すことで表現する。

数値には単位、対象期間、観測所、実測／推計、品質、データ版、計算版を添える。未来の予測値には発表時刻を追加する。欠けた値はnullと理由で返し、架空の値で画面を埋めない。

## 9. アプリ側のデータモデル

テーブル構成は[07_database.md](07_database.md)を正本とする。`field`・`field_weather_station`・`cultivation`・`cultivation_event`等の名称と関係は同編を参照する。

写真の保存先はCloudflare（2.3）、収量・品質の記録は04編のイベント詳細（メモ）、共有・貸借に伴うデータ引継ぎは07編6章の将来拡張として扱う。誰の記録を誰が引き継げるかを明確にしてから実装する。

## 10. 公開・認証・運用

本人利用のローカル試作と、外部農家への試用を分ける。外部試用前にHTTPS、認証、農地単位のアクセス制御、バックアップ、障害時の連絡方法を整える。農地の詳細位置や作業メモは初期状態で非公開とする。

ユーザーIDをクライアントの入力だけで信用せず、APIで認証済みユーザーと所有権を確認する。２ユーザーのテストで他者の農地IDを指定しても読み書きできないことを確認する。

最初の外部提供先は保留。自宅サーバーの回線・可用性・公開方法を評価し、必要ならAPIやDBを移す。Supabase移行時も画面は同じAPIを使える構成を基本とし、認証IDとの対応を管理する。地図のキーはプラットフォーム・接続元に適した制限を設定する。
