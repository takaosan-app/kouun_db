# 開発計画書 03：中盤・データ分析編

版：v0.9／更新日：2026-09-21  
到達目標：観測実績から、再現可能で説明できる集計・比較・異常値候補を作り、その上に作物別のリスク判定（L3）を載せる。

## 1. 基本方針

収集済みの気象観測値と気象庁公式平年値を、圃場ごとの栽培履歴と結び付け、
現在の生育状態で注意すべき気象条件や病害虫リスクを説明可能な形で示す。

最初の対象品目は次の2つとする。

- いちご（ハウスでの高設栽培を主な想定とする）
- 水稲

分析結果は農作業の自動指示や診断ではなく、農家が判断するための参考情報とする。
観測所の値を圃場やハウス内部の実測値として扱わない。

分析はPythonで実装する。最初は作物に依存しない機能を作り、その上に基準日からの積算など農業向け機能を追加する。生成AIは手法調査・実装・レビューに積極的に使うが、計算の正しさは入力例と検証で確かめる。

収集処理が元データと提供元品質を保持し、分析処理が利用条件・集計・判定を管理する。分析が失敗しても収集は継続する。欠測補完や異常値除去で元データを上書きしない。

## 2. 現時点の採用仕様

| 項目 | 計画上の採用内容 |
|---|---|
| 実行基盤 | Python、pandas、NumPy。機械学習は必要になった時点でscikit-learnを追加 |
| 入力 | 前半の正規化ビュー、観測所能力・位置履歴、項目辞書、品質 |
| 粒度 | 初期は日別。時別分析は収集対応後に追加 |
| 初期の分析単位 | 観測所×項目×期間。農地表示は参照観測所との関連を付ける |
| 実行時点 | 収集成功後に変更期間を再計算。手動の過去再計算も可能 |
| 開発形式 | ノートブックで探索し、採用処理は通常のPythonモジュールにする |
| 出力 | analysis_run、metric_result、anomaly_candidate、comparison_result |
| 判定の名称 | 「異常値候補」「近隣差」。誤測定や農業被害と断定しない |
| 初期の品質方針 | 公式の正常値を標準入力。準正常値等を含む表示は別設定で区別 |

分析は自宅サーバーのDocker Composeで定義するanalyzerサービスとして実行する。前半のcollectorと独立したジョブとし、収集成功後に起動する。探索用ノートブックを常時稼働の運用処理にしない。依存ライブラリを固定し、手動再計算も同じコンテナ環境で実行する。

## 3. データの四層構造

分析はこの4層の上で行う。層の役割、実装、アプリ向けDBへの同期範囲は次のとおり。

| 層 | 単位 | 役割 | 実装 | アプリ向けDBへの同期 |
|---|---|---|---|---|
| L0 原本・忠実層 | 配布原本／観測値 | 気象庁データを品質・出典・訂正履歴付きで保持 | `weather`スキーマ | しない |
| L1 軽量日次層 | 気象系列 × 日 | 必要な観測値を横持ち・10倍整数で保持 | `analysis.station_daily_weather` ほか | 直近18か月 |
| L2 日次派生指標層 | 気象系列 × 日 | 累積値等を利用者非依存で1日1回計算 | `analysis.station_daily_weather_feature` | 直近11年 |
| L3 リスク判定層 | 栽培案件 × 日 | 生育状態と基準日に依存する部分のみ計算 | 未実装 | する（アプリ向けDB側で計算） |

L1の台帳・能力・平年値は `analysis.weather_station`、`analysis.weather_element`、
`analysis.station_element_capability`、`analysis.station_daily_weather_normal` に持つ。
実装済みの件数と検証結果は[../STATUS_PLAN.md](../STATUS_PLAN.md)を参照する。

全体像としての四層の位置付けは[01_overall.md](01_overall.md)3章にある。本章は分析を
書くために必要な型設計と計算方式を扱う。

### 3.1 L1とL2で保持期間を分ける

アプリ向けDBでは、L1とL2で必要な期間が異なる。

| 層 | 期間 | 用途 |
|---|---|---|
| L1 | 直近18か月 | 日次グラフ、観測値の一覧。気圧・風向・積雪を含む全項目 |
| L2 | 直近11年 | 積算値、平年差、任意期間の過去比較、リスク判定 |
| 公式平年値 | 全期間 | 平年比 |

L2の11年は、過去比較のlookbackを最長10年とし、これに当年を加えた期間である。

L2は累積値であるため、任意の期間の集計は端点2行の引き算で求まる。過去何年分を比較する
場合でも読む行数は年数×2行にとどまり、応答時間は期間に比例しない。一方、その端点が
どこになるかは利用者の選択次第なので、対象年の日次行は保持しておく必要がある。

L1はL2から再計算しない。L2の累積値を隣接日で差分すれば、日平均・最高・最低気温、
降水量、日照時間、平均湿度、平均風速の7項目は10倍整数のまま誤差なく復元でき、欠測も
有効日数の累積が進むかどうかで判別できる。しかし風向コード、気圧、最低湿度、最大風速、
積雪深、降雪量、日別の品質マスクはL2に累積列がなく復元できない。容量の節約額に対して
失う項目が多いため、L1は独立して保持する。

18か月より前の日次値が必要になった場合、上記7項目に限ればL2からの差分で表示できる。
採用するかは画面設計時に判断する。

### 3.2 L0：原本・忠実層

L0は、ダウンロードしたCSV・ZIP等の原本と、現在の正規化済み観測値、観測所履歴、品質、
出典、取込・訂正履歴を含む。配布形式を忠実に取り込み、後からL1以降を再生成できることを
優先する。現在の気象DBは主にL0に相当し、容量の大きさ自体を問題とはしない。

### 3.3 L1：軽量日次層

L1はアプリと分析の共通入口とする。観測所または気象系列と日付で1行の横持ちテーブルにし、
雨量だけを観測する地点も同じテーブルへ格納する。気温、降水量、湿度、気圧、風速、
日照時間、積雪深等の連続量は、実値を10倍した`smallint`を基本とする。累積値は
`integer`とし、欠測は0ではなく`NULL`にする。風向、日数、回数、コード、ID、真偽値は
10倍しない。風向はコードとして保持し、降水量0.0mmと微量降水を区別するため、降雨の有無を
別の真偽値として持つ。

L1では詳細な品質情報を各値へ繰り返し持たせず、分析へ使用できるかを示す品質ビットマスク
等へ圧縮する。未観測、欠測、未取得、微量降水等の詳しい理由が必要な場合はL0へ戻る。
観測能力はL1の軽量な観測所・観測能力テーブルで判別できるようにする。
気象庁公式平年値も、配布原本と詳細な取込結果はL0に残し、比較表示と分析に使う値をL1と
同じ倍率・単位へ変換する。

### 3.4 L2：日次派生指標層

L2には気象系列の保持開始日からの累積値を持たせる。積算温度、有効積算温度、期間降水量は前方累積和で
表現できるため、区間値は次の引き算で求まる。

```text
区間の積算 = 累積[終了日] - 累積[開始日の前日]
```

田植え日や定植日が利用者ごとに異なっても、L3は日数分のループを行わず定数時間で済む。
栽培案件が増えても計算量は参照回数に比例するだけで、データ走査量は増えない。

### 3.5 L3：リスク判定層

L3の計算時にL0またはL1を期間走査する実装にすると、利用者数の増加がそのままDB負荷に
なるため採用しない。利用者に依存しない計算はL2で事前に行う。

## 4. L2で事前計算する指標

### 4.1 L2に置く指標

L1の日次値から、期間集計に繰り返し使用する値をL2で累積化する。

- 日平均・最高・最低気温を使った各積算温度
- 降水量と日照時間の累積値
- 閾値フラグの累積（降雨日数、高温日数、低温日数、日照不足日数）
- 連続降雨日数、連続無降雨日数（その日時点の値は気象系列と日付で決まるため直接保持）
- 時別値から落とした日次集計（湿潤推定時間、閾値超過時間数、感染好適条件フラグ）
- 有効日数の累積（6.1）

閾値フラグは後から閾値を変えると累積列の作り直しになるため、病害虫ルールで使う可能性の
ある閾値（降水量0mm超、1mm、5mm、10mm等）は最初から複数列を用意する。

### 4.2 累積和にできないもの

- 期間内の最大値・最小値。区間走査が必要だが、区間は長くても150日程度
- 前日の状態に依存する逐次モデル。発育段階によって係数が変わる形式のものは順次計算する

いずれも日次バッチとしては問題にならない規模である。

### 4.3 差分更新

通常の日次更新は、前日の状態に1日分を加算するのみとする。フル再計算を行うのは
栽培案件の新規登録時と、イベント日付の訂正時に限る。イベントに`recalc_from`を持たせ、
そこから当日まで再計算する。

L3の結果キャッシュのキーは利用者IDではなく、`(気象系列, 基準日, 算出日)`とする。
同じ気象系列・同じ基準日の利用者は1件の計算を共有する。基準日は地域ごとに集中するため、
利用者数に対して実際の計算パターン数は大幅に少なくなる。

## 6. 欠測・品質と集計のルール

分母の期待件数は、その観測所が対象項目を提供する期間から作る。未観測を欠測と数えない。取得待ち・取得失敗と提供元の欠測を別に数える。

利用可能率は「採用可能な値の件数÷期待件数」。初期の内部基準として、期間平均は90%以上で正式な集計値を返す。90%未満なら参考値または算出不可とし、有効件数と期待件数を必ず返す。この90%は本アプリの仮の基準であり、気象庁の品質判定基準ではない。

降水量合計・積算温度・高温日数は、期間内の不足がある場合に完全な期間値として返さない。参考用の「取得できた日の合計／日数」を別の値として表示できる。連続日数は欠測をまたいで連続とせず、「欠測により判定不明」を表す。

公式の日平均値と、独自に時別値を平均した値は別の指標にする。日最大風速、日平均風速等も別項目。風向は度数の単純平均・差を使わず、初期は表示だけにして円周上の統計は後続とする。

提供元の推計値は「推計」として利用可能にするが、実測と混ぜた比較は構成を明示する。観測環境の変更が分かる区間は分けて扱い、履歴不明の比較には注記を付ける。

### 6.1 累積値と有効日数を並べて持つ

降水と日照の欠測を0で埋めてはならない。欠測と「降水0mm」「日照0時間」は意味が異なり、
累積和にした時点で区別できなくなる。

累積値と並べて有効日数の累積を保持する。

```text
obs_date    precip_cum   precip_valid_cum
2026-05-01    412.5           121
2026-05-02    412.5           122   ← 降水0mm、観測あり
2026-05-03    412.5           122   ← 欠測（累積が進まない）
```

区間の欠測数も同じ引き算で求まるため、有効件数・期待件数・欠測率が同一クエリで得られる。
欠測率が閾値を超えた場合に判定自体を出さない制御も、1回の比較で済む。

## 7. 近隣観測所の選定と差異分析

アメダスを使う場合、圃場ごとに単一の参照観測所を持つ設計は成立しない。降水量のみの
観測点が多く、気温・日照が揃う観測点は限られる。要素ごとに参照観測所を持たせる。

初期対象の5県120観測所で確認した観測能力は次のとおり。

| 要素 | 観測地点 | 割合 |
|---|---:|---:|
| 日降水量 | 120 | 100% |
| 日平均・最高・最低気温 | 76 | 63% |
| 日照時間 | 73 | 61% |

降水量は全地点が観測するが、気温と日照は4割の地点にない。最寄りが雨量専用の場合、
気温は別の地点を参照することになる。

標高差も無視できない。気温は標高100mあたり約0.6℃変化する。

圃場登録時は要素ごとに候補を3地点提示し、利用者に選んでもらう。降水量は3地点とも使い、
気温と日照は主参照1地点を選ぶ。距離と標高差を必ず併記し、地形の判断は利用者に委ねる。
画面の詳細は[06_application.md](06_application.md)4.1にある。

風速と湿度は初期版では参照観測所の選択対象に含めない。風速は地形の影響が大きく、
距離でも標高差でも代替しにくい。L2には累積値を蓄積し続けるため後から追加できる。

初期の候補検索半径は50km、比較用は最大５地点、集約比較に必要な他地点数は３地点とする。これらは仮の設定であり、地域の地形や観測密度で見直す。

1. 対象日・項目に対応する観測所を検索する。
2. 対象時点の位置・標高、距離、利用可能率、実測／推計を付ける。
3. まず距離順に候補を示し、主参照・比較参照を利用者が変更できるようにする。
4. 同一日・同一項目・同一定義の値だけで差を計算する。
5. 集約比較では他地点の中央値と対象値との差を返す。対象地点自身は基準に含めない。

標高差200m以内を初期の比較候補条件とするが、標高が不明な候補は「条件未確認」とする。条件を満たす３地点がない場合、ペア比較は返せるが近隣集約の異常判定は行わない。半径を自動拡大して無条件に比較可能とは扱わない。

海沿い・盆地・都市化・局地降雨などによる本当の差がある。近隣差はまずそのまま見せ、自動的に標高補正や農地補間を行わない。将来の補間は交差検証を通し、「農地の推定値」として提供する。

降水量の差はmmを基本とし、比較元がゼロのとき比率は算出不可。少量の雨では比率が極端になるため、差の値も必ず表示する。

藤枝市稲川の初期サンプルでは、気温は静岡・静岡空港のペア比較、雨量は高根山を加えた比較から始める。島田は提供期間を確認するまで現行比較に数えない。これでは「他地点３地点」の条件を満たさないため、近隣集約の異常判定は保留し、ペア差を先行する。高根山は標高差による参考比較であることも示す。集約比較が必要になった時点で追加地点を選ぶ。

## 8. 異常値候補の判定

初期は説明しやすい方法に絞り、項目ごとの設定として管理する。

| 方法 | 初期仕様 | 制約 |
|---|---|---|
| 値の整合性 | 負の降水量、湿度0～100%の外などを検出 | 欠測記号・単位の誤変換を先に除く |
| 時間変化 | 前の有効な連続日との差を記録 | 欠測を飛ばした日差を１日の急変としない。閾値は項目別に実データで設定 |
| 頑健な外れ値 | 気温の日平均等に対し、過去30日・有効20日以上の中央値とMADを使用 | 当日・未来は基準に含めない。MAD=0なら判定保留 |
| 近隣差 | 他地点中央値との差を数値表示 | 気象の地域差と測器異常を区別できないため、単独で誤測定判定しない |

MADを使う初期スコアは `0.6745 × (対象値 − 基準中央値) ÷ MAD`、絶対値3.5以上を候補とする。この設定は試作の出発点であり、気象分野の確定した運用閾値ではない。降水量のようにゼロが多く偏った分布には、そのまま適用しない。

気温でも季節変化で候補が増える可能性があるため、実データで候補数・理由をレビューし、後続で季節別基準に改善する。データを数年に拡大した段階で、年をまたぐ学習・評価の分離を行う。

## 9. 年次比較・農業向け基準日集計

初期の前年比較は同じ暦日範囲で行い、うるう日の対応を明示する。生育イベント比較は「基準日から何日目か」でそろえる。基準日が未登録なら計算せず、農家が後から日付を修正できるようにする。

| 指標 | 定義・扱い |
|---|---|
| 単純積算温度 | 対象期間の日平均気温の和。単位は℃・日。負の値を切り捨てる別方式とは区別 |
| 有効積算温度 | `Σ max(日平均気温 − 基準温度, 0)`。初期は基準温度を指定した場合のみ計算 |
| 基準日以降の降水量 | 重複しない日降水量の和。欠測時は不完全とする |
| 高温日数 | 指定した最高気温の閾値以上の日数。初期UIの例は30℃、閾値は設定可能 |
| 少雨・無降水の継続 | 判定雨量を明示し、欠測日は継続を不明とする |
| 年比較 | 同一項目・期間・品質条件による差。分母ゼロでは比率を返さない |

基準日は指定日を含め、日別値が利用可能な最終日までとする。開花・満開・播種等のイベント種別、作物・品種、対象年、主参照観測所を結果に残す。

高温日数等を、そのまま「みかんの日焼け被害」「収穫適期」「病害発生」と言い換えない。作物別の判断モデルには別途、地域・品種・栽培条件に合う研究根拠と検証が必要。公式の平年値を導入するまでは、過去３年の平均を「平年」と表示しない。

## 10. 降水の扱い

### 10.1 誤りの非対称性

```text
観測所で降雨あり、圃場で降っていない  → 空振り。害は小さい
観測所で降雨なし、圃場で降っていた    → 見逃し。防除適期を逃す
```

見逃しの損失が大きいため、判定の閾値は前広に倒す。

### 10.2 前広さと通知の強さを分離する

閾値を下げると通知頻度が上がり、梅雨期に通知が無視されるようになる。判定の前広さと
通知の強さを分けて設計する。

```text
判定       前広（近隣の降雨で条件成立の可能性を立てる）
プッシュ   保守的（観測所で明確に降雨がある場合のみ）
アプリ内   前広（「近隣で降雨の可能性」を常時表示）
```

### 10.3 近傍の複数観測所を参照する

最寄り1点ではなく、半径20〜30km程度の観測所を3〜5点参照する。

```text
島田 0.0mm ／ 金谷 8.5mm ／ 川根本町 15.0mm
→ 圃場では降っていない可能性が高いが、北側で降雨
```

降水域が近傍を通過したかが把握でき、最寄りが0mmであることの確からしさも上がる。
L1・L2は気象系列×日で保持されているため、複数系列の参照は追加コストがほぼない。
`field`には最寄り1点ではなく、距離付きの近傍観測所リストを持たせる。

### 10.4 量ではなく有無と日数で判定する

解析雨量のバイアス（[02_data_collection.md](02_data_collection.md)4.3）と、病理上の意味の両面から、降水量の総和で閾値を切らない。

```text
✕ 3日間で30mm以上
◯ 3日間のうち降雨日が2日以上
```

炭疽病も葉いもち病も、効くのは濡れていた日数である。メッシュデータに
「1mm以上の降水の有無（OPR）」が用意されているのも同じ用途である。

### 10.5 解析雨量を購入する価値

APCPRAの価値は「利用者に尋ねなくても降雨の有無が分かる」ことにある。利用者の記録
（[04_cultivation_state.md](04_cultivation_state.md)10章）が得られる場合、その価値は下がる。記録の取得率によって判断する。

```text
APCPRA     月3,300円、1kmメッシュ、観測点周辺のバイアスあり、地形遮蔽あり
利用者記録 無償、圃場そのもの、ただし記入率に依存
```

11月のモックで記入率を測定してから判断する。

### 10.6 圃場ごとの降雨系列を作る

参照する3地点を別々に判定して並べない。「島田では3日連続、金谷では5日連続」と示されても、
農家はどう動けばよいか判断できない。3地点と日誌の記録を合成し、圃場ごとに1本の降雨系列を作る。

その日の降雨判定は次の順に決める。

| 順 | 条件 | 判定 |
|---|---|---|
| 1 | 日誌に記入がある | 日誌の記録を使う。圃場そのものの記録であるため最優先 |
| 2 | 記入がなく、3地点のいずれかで降雨あり | 降雨日とする |
| 3 | 記入がなく、3地点とも降雨なし | 降雨なしとする |
| 4 | 記入がなく、3地点とも欠測 | 判定不能。0で埋めない |

「いずれか1点でも降雨あり」とするのは、見逃しの損失が空振りより大きいためである（10.1）。
2点以上を要求する多数決も考えられるが、見逃しが増えるため採らない。

観測所と日誌が食い違う場合は、一方で他方を上書きせず両方を保持し、どちらを用いたかを
結果に明示する（13章）。

この合成により、L2の`consecutive_rain_days`はそのまま使えなくなる。L2の連続日数は
観測所ごとの値であり、合成後の系列では数え直す必要がある。このため圃場×日付の
降雨系列をL3に持つ。

```text
圃場 × 日付
  降雨あり／なし／判定不能
  判定根拠（日誌／観測所の合成／主参照のみ）
  使った観測所と各観測値
  連続降雨日数、連続無降雨日数
```

前日の状態に1日を加える増分更新とし、圃場が増えても1圃場1日1行に収まる（3.3）。
日誌が後から入力または訂正された場合は、その日を`recalc_from`としてそれ以降を再計算する。

この系列は圃場に依存し、栽培案件には依存しない。リスク判定より1段手前の層として扱う。

気温と日照は主参照1地点を使うため合成は行わず、L2の値をそのまま参照する。

## 11. いちごの分析

### 11.1 栽培経路

最初に想定する経路は次の3つである。

1. 育苗開始から本圃で管理する
2. 苗場で育苗し、その後に本圃へ植え替える
3. 苗場で育苗し、冷蔵処理後に本圃へ植え替える

「本圃へ直接植える」場合も、生物学的な育苗期がなくなるわけではない。育苗期を
本圃で過ごすか、苗場で過ごすかの違いとして扱う。

```text
本圃開始
育苗期（本圃）→ 花芽分化 → 開花 → 収穫

苗場開始
育苗期（苗場）→ 本圃定植 → 花芽分化 → 開花 → 収穫

苗場・冷蔵あり
育苗期（苗場）→ 冷蔵処理 → 本圃定植 → 開花 → 収穫
```

低温処理には夜冷短日処理、暗黒低温処理（株冷）、間欠冷蔵処理等があるため、最初から
方式名を決め打ちしない。冷蔵中の明暗、温度、期間、連続処理か出し入れを伴うかを任意の
詳細条件として記録する。

### 11.2 主要イベント

- 育苗開始
- 冷蔵開始
- 冷蔵終了
- 本圃定植
- 花芽分化確認
- 開花開始
- 収穫開始
- 収穫終了
- 病害虫確認

いちごは花房が繰り返し発生する。初期版では最初の開花開始を主要イベントとし、花房ごとの
記録は必要性を確認してから追加する。

### 11.3 状態の例

```text
育苗開始（本圃）             → 本圃・育苗中
育苗開始（苗場）             → 苗場・育苗中
冷蔵開始                     → 冷蔵処理中
冷蔵終了、本圃定植前         → 定植待ち
本圃定植                     → 本圃・定植後
開花開始                     → 開花期
収穫開始                     → 収穫期
収穫終了                     → 栽培終了
```

病害虫や生育リスクのルールは、3つの栽培経路へ直接結び付けず、まず育苗期、定植後、
開花期、収穫期等の生育状態へ結び付ける。その上で場所、施設、培地、灌水方法、温湿度等で
条件を補正する。これにより、育苗期に共通する注意点をすべての経路へ適用できる。

### 11.4 気象データの限界と、育苗期への集中

高設いちごではハウス内部の温湿度、培地温度、給液量、EC等が重要である。気象庁データ
だけで判断できるのは、外気温、降水、日照、換気・暖房負荷等に関係する外部条件までとする。

一方、育苗期は露地または雨よけで行われるため外気が直接影響し、かつ炭疽病は育苗期に
大きく左右される。屋外気象データで意味のある判定ができる範囲が育苗期に集中している。

このため、いちごの初期版は育苗期に絞る。定植後は外部条件の参考値表示に留める。

冷蔵処理中は外部の気象観測値を処理温度の代用にしない。設定温度または冷蔵庫内の実測値を
利用し、未入力の場合は詳細な低温処理判定を行わない。

## 12. 水稲の分析

### 12.1 主要イベントと状態

水稲も同じ状態管理基盤を使う。

```text
播種 → 育苗 → 移植 → 分げつ → 出穂 → 登熟 → 収穫
```

初期の主要イベント候補は次のとおり。

- 播種
- 育苗開始
- 移植
- 出穂開始または出穂期確認
- 収穫開始
- 収穫終了
- 病害虫確認

分げつ、幼穂形成、登熟等は、利用者による実績入力と気象・経過日数による推定を分ける。
現場で入力負担が大きいイベントは、最初から必須にしない。

### 12.2 初期分析候補

実装の難易度順に整理する。

| 対象 | 指標 | 必要データ |
|---|---|---|
| 出穂期推定 | 有効積算温度 / DVI | 日別 |
| 白未熟粒リスク | 出穂後20日間の平均気温 | 日別 |
| 生育の進み・遅れ | 平年差 | 日別 |
| 高温・低温遭遇 | 閾値超過日数 | 日別 |
| 日照不足 | 日照時間の平年比 | 日別 |
| 葉いもち | BLASTAM系の感染好適条件 | 時別 |

時別データを要求するのは葉いもちのみである。これを採用するか否かが、時別データを
保持するかの分岐点となる（[02_data_collection.md](02_data_collection.md)8章）。

病害虫、障害、作業適期を気象値だけで断定しない。品種、栽培暦、水管理、地域条件等を
含む根拠資料を調査し、検証済みのルールだけを採用する。

### 12.3 田植え日の扱い

大井川流域のように用水の通水が順番制の地域では、田植え日が割当日に依存する。単純な
基準日からの積算ではなく、割当日から逆算する計算が必要になる。水が豊富で自分で決め
られる地域もあるため、複数パターンを用意する。

なお、田植え日が利用者ごとに異なっても計算量は増えない（3.4）。また地域ごとに日付が
集中するため、実際の計算パターン数は利用者数より大幅に少ない。

### 12.4 機械学習は採用しない

発生実績の教師データがなく、初期の利用者も限られるため、機械学習は現時点で成立しない。
既存の確立モデルの移植とルールベースを採用する。

ただし病害虫確認イベントと日誌の自由記述は、将来の検証データとして最初から蓄積する。

## 13. リスク判定の考え方

現在のリスクは次の情報から計算する。

```text
圃場と栽培案件
＋ 現在の生育状態
＋ 状態開始からの経過日数
＋ 品種と管理条件
＋ 直近の気温・降水・日照
＋ 気象庁公式平年値との差
＋ 利用者の日誌記録（降雨の有無等）
＋ 施設内センサー値（存在する場合）
＝ 現在想定される生育・病害虫リスク
```

結果には少なくとも次を付ける。

- 現在状態と、確認済み／推定の区別
- リスク名と段階
- 判定対象期間
- 使用した気象系列・項目・値（観測所名、距離、標高差を含む）
- 有効件数、期待件数、欠測
- 判定ルールと版
- 利用者の日誌記録を使った場合はその旨
- 根拠資料
- 制約と、利用者に確認してほしい事項

「危険」の一語だけを返さず、何を根拠にした参考情報かを説明する。屋外観測値のみの場合は
施設内の状態を直接測定した判定ではないことを明示する。

観測所と日誌の記録が食い違う場合（観測所で降雨なし、日誌で降雨あり等）、一方で他方を
上書きせず両方を保持し、どちらを用いたかを結果に明示する。

欠測の扱いは6.1を参照する。判定に使える有効日数が不足する場合は、リスク判定自体を出さない。

## 14. 根拠資料の扱い

病害虫や生育条件は、気象庁、農研機構、都道府県の農業試験場、大学、査読論文等を優先して
調査する。品種・地域・作型が異なる試験結果を、そのまま全国共通の閾値にしない。

いちごの低温処理について確認済みの参考資料：

- [間欠冷蔵処理によるイチゴの花芽分化促進（農研機構）](https://www.naro.go.jp/publicity_report/publication/pamphlet/tech-pamph/046075.html)
- [イチゴの花芽発達に悪影響を及ぼす高温遭遇の程度（農研機構）](https://www.naro.go.jp/project/results/laboratory/warc/2007/wenarc07-20.html)
- [イチゴのトレイ苗への短期間冷蔵処理による花芽分化誘導技術（農研機構）](https://www.naro.go.jp/project/results/5th_laboratory/warc/2024/warc24_s06.html)
- [静岡県のイチゴ栽培技術資料](https://www.pref.shizuoka.jp/_res/projects/default_project/_page_/001/058/706/01_ichigo_manual.pdf)

これらは方式の存在と検討項目を確認するための資料であり、本アプリの判定閾値としては
まだ採用していない。

気象データの性質に関する参考資料：

- メッシュ農業気象データ利用マニュアル（農研機構）
- 配信資料に関する仕様 No.11601 解析雨量・速報版解析雨量（気象庁）
- 国土交通省「解析雨量」と地上観測雨量との比較（玉川ほか、岐阜大学）

検証時期が古い資料については、その後の改良の有無を確認する。

## 16. 生成AIの活用手順

1. 分析課題を１つ選び、必要な入力・出力・利用場面を定める。
2. 気象庁、農研機構、大学・学術論文、ライブラリ公式資料を優先して調べる。
3. 候補手法を、必要データ、仮定、説明のしやすさ、検証方法で比較する。
4. 採用案を小さい入力で実装し、手計算・既知例と照合する。
5. 実データで候補をレビューし、採否・根拠・限界を記録する。
6. 採用した式・閾値・設定・コード版を固定し、運用処理へ移す。

AIの調査結果は `research_notes` に、問い、出典URL、確認日、手法、採否、未検証事項として残す。初期アプリの動作に生成AI呼出しは必須にせず、指標は決定的な計算で返す。AIによる文章説明を追加する場合も計算済み結果を入力とし、出典にない数値を生成させない。

将来の機械学習候補にはIsolation Forest等があるが、初期のルール・統計手法を比較基準にする。学習済みデータの外れ値検出と未知データへの検出は、評価条件を分ける。[scikit-learn公式解説](https://scikit-learn.org/stable/modules/outlier_detection.html)

## 17. 再現性・APIへの受け渡し

分析結果には次を付ける。

- 分析名・版、実行ID、コード版、設定値、実行時刻。
- 入力データ版、対象観測所・項目・期間、参照地点、使用した品質条件。
- 結果の値・単位、有効件数・期待件数、算出可否、候補理由、制約。
- 基準日・参照観測所の設定版。予報導入後は発表時刻も含める。

元データ訂正時は影響期間を再計算する。30日の移動窓なら変更日の後30日も対象になり得る。基準日集計や年比較は関連する全結果を失効扱いにし、再計算完了後に最新版として公開する。処理途中の結果を完成済みとして出さない。

農地そのものの実測がない場合、結果は「参照観測所による集計」として返す。アプリ側で独自に計算式を再実装せず、PCとスマホで同じAPI結果を使う。

## 18. 検証と完了条件

| 検証 | 合格条件 |
|---|---|
| 手計算できる小データ | 平均、合計、日数、積算が一致。丸め前は許容誤差内 |
| 欠測・未観測・未取得 | ゼロ扱いされず、算出可否と分母が正しい |
| 近隣比較 | 自地点を基準から除外し、時刻・項目をそろえる |
| 異常値候補 | 作為的に追加した負の雨量・単位誤り・突出値を適切に区別 |
| 境界ケース | MAD=0、比較元ゼロ、うるう日、移転、基準日変更を扱える |
| 再現・訂正 | 同じデータ版・設定で同じ結果。訂正後は影響する結果だけ更新 |
| 実データレビュー | 少数地点・１年分から最低30件の候補／通常例を人が確認し、理由を説明可能 |

ラベル付きの正解データがない段階で「検出精度○%」とは主張しない。レビューした候補数・有用だった件数・見落とし事例を記録し、通知への採用はその後に判断する。

A1～A5について、検証例、実データ結果、設定、データ辞書がそろえば初期完了とする。UI完成や全国収集完了は条件にしない。

## 19. 保留事項

季節別の基準期間、項目別急変閾値、平年値、作物・品種別モデル、標高補正、農地への補間、機械学習の採用は実証後に決める。いずれも未実装のまま利用者に判定結果を見せない。

作物別分析（L3）について、設計上の判断で内部で決めるものは次のとおり。

- 葉いもち（BLASTAM系）を採用するか。時別データの保持方針が連動する
- 最初に対象とするいちごの品種
- 実際の冷蔵処理方式、温度、期間、明暗条件
- 本圃と苗場の位置が同じか、別の気象系列を参照するか
- ハウス内センサーを導入する時期と項目
- 水稲の品種、播種・移植方式、対象地域の栽培暦
- 生育状態を推定する式と必要な実績イベント
- 病害虫ごとの条件、根拠、表示方法、通知条件
- 同じ圃場内の区画・複数品種への対応時期
- 日誌の記入率がどの程度になるか（APCPRA購入判断に連動）

外部への問い合わせが必要な事項は[BUSINESS.md](../BUSINESS.md)にまとめる。
