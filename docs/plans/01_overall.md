# 開発計画書 01：全体編

版：v0.7／更新日：2026-09-21
目的：大きな流れと機能を共有する。詳細設計は各編を正本とする。

## 1. 目指すもの

農地の位置、気象実績、作物・作業の記録を結び付け、農家自身の判断材料を増やす。過去から現在までの履歴を蓄積し、将来は予報も同じ画面で参照できるようにする。

初期の利用場面は「この地域で最近どのくらい雨が降ったか」「近くの別の観測所とどの程度違うか」「今年は昨年と比べてどうか」「開花日以降の積算温度はどの程度か」。農作業を自動で指示する機能は初期の目的にしない。

想定する試用先は、本人の利用に続いて、実家の田んぼの利用者や、みかん・イチゴなどを栽培する身近な農家。参加はまだ確定していない。

サンプル地域は静岡県藤枝市稲川。静岡・静岡空港・高根山を現行データの候補、島田を観測期間の確認が必要な過去データ候補として、項目の違いを検証する。詳細は前半編2Aを参照。

リポジトリ直下の`AGENTS.md`にある**AIへの依頼およびユーザーの方針**は常に意識し、曖昧な指示には必ず確認すること。

## 2. 全体構成

```text
気象台・観測所の公開データ
         ↓ Pythonで取得・整形・品質確認
自宅サーバー：PostgreSQL＋PostGIS ＋ 元ファイル保存（L0・L1・L2を全国・全期間）
         ↓ 配信範囲のみ同期
アプリ向けDB：Supabase（利用者・圃場・栽培案件・イベント・L3結果）
         ↓ API（GCPで実行。現在の案）
Flutter：PCブラウザ／Android／iPhone

日誌画像：Cloudflareへ保存し、DBにはオブジェクトキーを持つ
後から追加：農地ポリゴン、降水予報・ナウキャスト、現地センサー
```

本書は全国を対象とした仕様を定める。アプリ向けDBへ同期する範囲と、初期版で対象とする
地域は[06_application.md](06_application.md)で定める。

前半・中盤は自宅サーバー上のDocker Composeで構築する。DB・収集・分析を別サービスとして定義し、DBは常駐、収集と分析は必要なタイミングに実行する。DBと元ファイルはコンテナの外に永続化する。

収集、分析、API、画面を独立した役割として実装する。初期は同じサーバー・リポジトリでよく、収集を止めずに分析や画面を変更できる構成にする。

役割の配置は次のとおり。

```text
自宅サーバー   L0、取り込みETL、L1・L2生成
Supabase       必要なL1・L2、利用者データ、圃場、栽培案件、イベント、ルール評価、L3の結果
GCP            バックエンドAPIの実行（現在の案）
Cloudflare     日誌画像の保存
```

自宅サーバーが停止してもアプリは動作し、当日の結果が更新されないだけの状態にする。ETLは冪等とし、停止した日は翌日まとめて再実行できる形とする。

L0を Supabase に置かない。データ量と転送量に対して費用効率が悪い。アプリで必要な期間・地域・項目に絞ったL1とL2だけを同期する。

## 3. データの四層構造

観測データを4つの層に分けて持つ。層ごとに責任を分け、下の層から上の層を再生成できるようにする。

| 層 | 単位 | 役割 |
|---|---|---|
| L0 原本・忠実層 | 配布原本／観測値 | 気象庁データを品質・出典・訂正履歴付きで保持 |
| L1 軽量日次層 | 気象系列 × 日 | 必要な観測値を横持ち・10倍整数で保持 |
| L2 日次派生指標層 | 気象系列 × 日 | 累積値等を利用者非依存で1日1回計算 |
| L3 リスク判定層 | 栽培案件 × 日 | 生育状態と基準日に依存する部分のみ計算 |

L0は配布形式を忠実に取り込み、後からL1以降を再生成できることを優先する。L1はアプリと分析の共通入口とする。L2は利用者に依存しない計算を先に済ませ、利用者ごとに基準日が違ってもL3が定数時間で済むようにする。

アプリ向けDBへ同期するのはL1の一部とL2以降であり、L0は自宅サーバーに留める。

各層の型設計、累積値の求め方、実装テーブルとの対応は[03_data_analysis.md](03_data_analysis.md)3章を正本とする。

## 4. 計算はサーバーで行う

端末側での計算は採用しない。理由は性能ではなく構造である。

- 気象由来の指標は観測所またはメッシュと日付で決まり、利用者数に依存しない。
  一度計算すれば全利用者で使い回せる。端末計算では同じ計算を人数分行う
- 事前警告・通知は、サーバーが条件成立を検知しなければ発報できない
- 「判定ルールと版」を記録して再現する設計は、ルールを中央で管理しなければ成立しない。
  アプリの版によって判定が変わる状態は許容しない

端末の役割は表示と入力に限定する。オフライン閲覧用に直近の結果をキャッシュする程度とする。

## 5. 機能の全体像

| 領域 | 初期版に含む | 後続で拡張する |
|---|---|---|
| データ取得 | 少数地点の日別観測値、CSV取込、過去分・定期取得 | 時別値、対象地域・期間の拡大、全国対応 |
| データ管理 | 観測所・項目一覧、品質情報、出典、再取得・訂正、バックアップ | より詳細な移転履歴、大容量対策、クラウド移行 |
| 地理情報 | 観測所の位置、農地ピン、近隣観測所 | 筆ポリゴン、標高・地形・土壌等 |
| 汎用分析 | 期間集計、欠測率、異常値候補、近隣差、前年比較 | 季節基準、機械学習、空間補間 |
| 農業向け分析 | 任意基準日からの積算温度・降水量、高温日数 | 作物・品種別指標、収量・品質との関係 |
| アプリ | 農地登録、観測履歴、複数観測所比較、メモ・基準日 | 写真、通知、共有、より充実したオフライン利用 |
| 未来の気象 | 初期版では未提供と明示 | ナウキャスト、数時間先降水予報、予報の検証 |
| 現地データ | 接続可能な設計を残す | ハウス内温湿度、水田センサー等 |
| 利用者・事業 | 本人利用→少人数試用、アクセス権 | 農家間共有、JA・生産部会、課金・契約 |

観測所の実績、格子の解析値、予測値、現地センサーの測定値は、出典・時刻・意味を区別する。アメダスの観測実績は「観測所データ」の一部であり、別系統として重複登録しない。

## 6. 開発順序と区切り

| 段階 | 得られるもの | 次へ進む条件 |
|---|---|---|
| 前半：収集・DB | 同じ手順で取得・復旧できる観測データ基盤 | 少数地点で継続運用し、品質・重複・復元を確認 |
| 中盤：分析 | 同じ入力から同じ結果を再現できる分析処理 | 手計算と一致し、欠測時は不足を示す |
| 後半：アプリ | PC・スマホから農地と気象履歴を参照・記録 | 実機で基本操作でき、本人以外のデータを保護 |
| 実証・拡張 | 利用者の反応に基づく改善 | 必要性、費用、取得経路を確認して追加 |

全国取得が終わるまで分析・アプリを待つ必要はない。小さな対象範囲で３段階を一度つなぎ、収集範囲はその後に広げる。

日程は固定せず、各編の完了条件で進捗を判断する。個人開発で他の開発と並行するため、初期試作の実測から作業量を見直す。全国の過去分取得に必要な待ち時間は、開発時間とは別に見積もる。

## 7. 現時点の技術方針

| 項目 | 方針と状態 |
|---|---|
| 収集・分析 | Pythonを計画上採用。既存の不動産データシステムの経験を生かす |
| 取得方法 | CSV等の配布データを優先。HTML解析は補完手段 |
| DB | 自宅PostgreSQL＋PostGIS。アプリ向けDBはSupabaseを採用案とする |
| API | Python＋FastAPIを計画上採用 |
| 画面 | ユーザーの希望を踏まえてFlutterを計画上採用 |
| アプリ向け配信 | L1は直近18か月、L2は直近11年を同期。標準PostgreSQL中心に設計 |
| 実行場所 | バックエンドAPIはGCPを現在の案とする。画像保存はCloudflare |

SupabaseのPostGIS対応、FlutterのWeb・モバイル対応は公式資料で確認できる。実際の移行条件や対応OSは実装時に再確認する。[Supabase](https://supabase.com/docs/guides/database/extensions/postgis)、[Flutter](https://docs.flutter.dev/platform-integration/web)

### Pythonソースの分割方針

- １ファイル１責務を基本とし、250行を超えた時点を構成見直しの目安にする。
- 250行を超える場合は、CLI、設定、外部通信、ファイル保存、解析、DB操作などの責務で分割できないか確認する。
- `__main__.py` 等のエントリーポイントは引数の受付と処理の呼び出しを中心とし、業務処理を詰め込まない。
- CSV解析とDB登録のように個別検証できる処理は分離し、ネットワークやDBがなくても単体で確認できる構成にする。
- 行数を減らすためだけに細かく分割しない。関連する処理を１ファイルに置く方が分かりやすい場合は、250行を超えても一体性と読みやすさを優先する。

## 8. 特に大切な設計上の判断

- 農地に近い観測値は参考値。農地そのものの実測とは表示しない。
- 欠測、未観測、未取得、取得失敗を分け、欠けた値をゼロにしない。
- 異常値候補は元データを消す理由にせず、別の分析結果として保持する。
- 日別実績から始める初期版は、リアルタイム監視や警報の用途を前提にしない。
- 通知は利用者が必要なものを選ぶ。外気観測値でハウス内部の温湿度を代用しない。
- ナウキャストのみで数時間先予報を賄えるとは扱わず、予報時間に合う製品を選ぶ。
