# 開発計画書 07：DB設計編

版：v0.1／更新日：2026-09-21  
状態：概念設計（テーブルと関係のみ。列・型・制約は未確定）  
到達目標：気象データと利用者データを分けたまま、栽培状態からリスク判定までを再現可能に表現する。

本編はL3のDB設計を扱う。栽培イベントと状態の業務仕様は[04_cultivation_state.md](04_cultivation_state.md)、
分析とリスク判定の考え方は[03_data_analysis.md](03_data_analysis.md)を正本とし、本編は
それらをテーブルへ落とす方法を扱う。

## 1. 設計の前提

これまでに確定した判断を再掲する。根拠は各編にある。

| 前提 | 内容 | 根拠 |
|---|---|---|
| 管理単位 | 利用者 → 圃場 → 栽培案件 → イベント。農場の階層は設けない | 04編2.1 |
| 圃場の粒度 | 作物ごとに別の圃場として登録する | 04編2.1 |
| 主キー | 利用者データはUUID。端末側で採番する | 本編2.2 |
| 所有の判定 | 各テーブルに利用者を非正規化して持つ | 本編2.3 |
| 正本の所在 | 利用者データはアプリ向けDB。気象データは自宅サーバー | 01編2章 |
| 開発の場所 | 自宅PostgreSQLの`app`スキーマで設計し、同じDDLをアプリ向けDBへ適用する | 本編2.4 |
| イベントの扱い | 現在状態を上書きせず、イベントから導出する | 04編2.2 |
| 削除 | 物理削除せず取消状態として扱う | 04編8章 |

## 2. 全体の構成

### 2.1 4つの区画

```text
━━━ リスク要因の時系列（利用者非依存・自宅から同期）━━━

  weather_element                気象要素の台帳
  weather_station                観測所マスタ（位置・標高）
  station_element_capability     観測所がどの要素を観測するか
  station_daily_weather          L1・日次の実測値（直近18か月）
  station_daily_weather_feature  L2・累積値と連続日数（直近11年）
  station_daily_weather_normal   公式平年値

━━━ マスタ（利用者非依存・版を持つ）━━━

  crop ─┬─ cultivar                    品目と品種
        └─ cultivation_event_type      品目別イベント種別の台帳
  crop_stage_rule                      イベントから状態を導出する規則
  input_spec_version                   入力項目の文言と閾値定義の版

━━━ 利用者データ ━━━

  app_user
   └─ field                            圃場・ハウス
       ├─ field_weather_station  →  weather_station
       │      要素 × 観測所 × 役割（主／比較）× 順位
       ├─ diary_entry                  日誌（天気チェック・自由記述・降雨記録）
       └─ cultivation                  栽培案件（作期×品目×品種×栽培方法）
            ├─ cultivation_event       栽培イベント（実績）
            │   └─ cultivation_event_revision   訂正・取消の履歴
            ├─ cultivation_state       導出した状態と開始日
            └─ cultivation_estimate    推定結果

━━━ 判定 ━━━

  risk_rule                            状態と環境条件に対応する版付き判定規則
   └─ risk_result                      判定結果と根拠（ログ）
```

第1段階は判定の2テーブルを除く19テーブル、判定を含めて21テーブルとなる。

### 2.2 圃場は気象値を持たない

雨・気温・日照はリスク要因の時系列であり、圃場や栽培案件の属性ではない。圃場が持つのは
「どの系列を見るか」の指定（`field_weather_station`）だけで、系列そのものは持たない。

判定は次の形になる。

```text
状態（開花期）＋ 状態の開始日（9/8）
  ＋ 参照系列（降水3地点・気温1・日照1）
  ＋ その期間のリスク要因時系列
  → risk_result に判定と根拠を記録
```

降水3地点と日誌の合成（03編10.6）も永続テーブルにせず、判定のたびに導出する。合成に
使った各観測所の値と採用した根拠は`risk_result`に残すため、後から判定を検証できる。
参照観測所を変更しても過去の判定結果を作り直す必要がない。

### 2.3 主キーと所有

利用者データの主キーはUUIDとし、端末側で採番する。理由は次のとおり。

- 日誌は後日まとめて入力されることがあり、圏外でも記録できる必要がある（06編2.2）
- 圃場ごとの通番をサーバーで採ると、複数端末が同じ番号を採って衝突する
- UUIDであれば再送しても同じ行になり、競合解決の仕組みを要しない

気象系のテーブルは自宅サーバーが単独で書くため、既存の`bigint`採番を維持する。

所有の判定は、各テーブルに利用者を非正規化して持つ方式とする。親テーブルを遡らずに
1列で判定でき、アプリ向けDBの行レベル権限と相性がよい。

### 2.4 開発と本番の場所

| | 場所 |
|---|---|
| 設計とテスト | 自宅PostgreSQLの`app`スキーマ |
| 本番の正本 | アプリ向けDB |
| 判定の実行 | アプリ向けDB側 |

判定の入力3つのうち、栽培状態と日誌はアプリ向けDBが正本であり、L2も配信分が置かれる。
自宅で判定すると日誌と状態を逆同期することになり、双方向同期が必要になるため採らない。

標準SQLの範囲で設計し、同じDDLを両方へ適用できる状態を保つ。

## 3. 区画ごとの役割

### 3.1 リスク要因の時系列

自宅サーバーから同期される読み取り専用のデータで、本編では構造を定義しない。
実装は[03_data_analysis.md](03_data_analysis.md)3章にある。

同期範囲はL1が直近18か月、L2が直近11年、公式平年値が全期間。対象は静岡県と接する
4県の120観測所（06編2.1）。

### 3.2 マスタ

`crop`と`cultivar`は品目と品種。品種は不明を許容する（04編5.1、6.1）。

`cultivation_event_type`は品目別のイベント種別を台帳として持つ。作物や状態をコードへ
直書きしない方針（STATUS_PLAN 4.2）のため、いちごと水稲のイベントはこの台帳の行になる。

`crop_stage_rule`はイベントから状態を導出する規則を持つ。`input_spec_version`は入力項目の
文言と閾値定義の版で、文言を変更すると過去データの意味が変わるため版を付けて保存する
（04編10.2）。

### 3.3 利用者データ

`field`は圃場・ハウス。位置と標高を持つ。標高はピン確定時に国土地理院の標高APIから
取得する（06編4.1）。

`field_weather_station`は要素ごとの参照観測所を持つ。降水量は3地点、気温と日照は
主参照1地点で、役割と順位を保持する（06編4.1）。

`diary_entry`は日誌。天気チェック、自由記述、降雨記録を含む。降雨記録を別テーブルへ
抜き出さない。日誌のデータとして一体で扱う。

`cultivation`は栽培案件。同じ圃場でも年または作期が異なれば別の案件とする（04編2.1）。

`cultivation_event`は実績イベント。病害虫確認と作業記録も専用テーブルを設けず、
イベント種別で区別したこのテーブルの行として扱う（04編4章）。

`cultivation_event_revision`は訂正・取消の履歴。誤登録は物理削除せず取消状態とし、
状態計算から除外する（04編8章）。

`cultivation_state`は導出した状態と開始日を持つ。開始日がリスク判定の基準日になる。
このテーブルは正本ではなく、`cultivation_event`から再生成できるキャッシュである
（04編12章）。

`cultivation_estimate`は推定結果。実績と分けて保持し、利用者が確認した時点で
`cultivation_event`の実績行になる（04編9章）。

### 3.4 判定

`risk_rule`は版付きの判定規則。リスク対象、対象作物・生育状態、使用するL2指標、閾値、
判定期間、重み、リスク段階と表示文、根拠資料、適用地域、適用開始日と廃止日を持つ
（STATUS_PLAN 4.3）。

`risk_result`は判定結果を記録する。現在状態と確認済み／推定の区別、リスク名と段階、
判定対象期間、使用した気象系列・項目・値、有効件数と期待件数と欠測、規則の版、
日誌記録を使った場合はその旨、根拠資料、制約を含む（03編13章）。

判定に必要な窓は最長180日とし、連続無降雨日数のような長期の連続判定もこの範囲で行う。

## 4. 依存の階層

同期と再計算の単位はこの階層で決まる。

| 依存先 | テーブル | 更新の契機 |
|---|---|---|
| 利用者非依存 | 気象6種、マスタ5種 | 自宅からの日次同期、規則の改版 |
| 利用者 | `app_user` | 登録時 |
| 圃場 | `field`、`field_weather_station`、`diary_entry` | 圃場登録時、日誌入力時 |
| 栽培案件 | `cultivation`、`cultivation_event`、`cultivation_event_revision`、`cultivation_state`、`cultivation_estimate` | イベント入力・訂正時 |
| 判定 | `risk_result` | 日次、イベント訂正時 |

イベントの訂正または取消が発生した最古の日を`recalc_from`とし、その日以降の状態と
判定を再計算する（04編8章）。

## 5. 列の設計で決める論点

本編の次の段階で決める。現時点では確定しない。

- `cultivation_event_revision`を別テーブルにするか、`cultivation_event`に版を持たせるか
- `cultivation_state`をスナップショットとして保存するか、都度計算するか
- `cultivar`を利用者が追加できるようにするか。品種不明を許容する仕様との兼ね合い
- イベント固有の詳細（冷蔵温度、株数など）を列にするかJSONを併用するか（04編12章の保留事項）
- 行レベル権限の具体的な方式と、`app_user`をアプリ向けDBの認証情報とどう対応させるか
- オフラインでの編集・訂正に備える列（更新時刻、端末、リビジョン）を初期版から置くか

## 6. 当面行わないこと

- 圃場ごとの気象値を永続テーブルとして持つこと
- 月次・年次の集計テーブル。対象5県では日次で足りるため、地域拡大時に再判断する
- 複数端末で同じ圃場を同時編集した際の調停
- 同じ圃場内の区画・複数品種への対応（04編13章）
