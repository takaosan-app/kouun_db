# 開発計画書 02：前半・データ収集編

版：v0.7／更新日：2026-09-21
到達目標：観測所の実績値を、品質と出典を保ったまま自宅DBに継続蓄積する。

## 現在の実装状況

- Docker Compose上にPostgreSQL＋PostGIS、収集・分析用ロール、`weather`・`analysis`スキーマを構築した。
- C1として静岡（`s47656`）の2026年8月の日別4項目を取得し、CSV・メタデータを保存してDBへ登録した。同じファイルの再取込で観測値が重複しないことを確認した。
- C2を開始し、静岡の2023年9月～2026年8月を月単位で取得した。36か月、4,384観測値、CSV・JSON各36ファイルを保持している。
- 品質コード8の正常値4,377件と、品質コード5の準正常値7件を値と分けて保持できている。訂正値、欠測、非観測の実データによる検証は未完了。
- 実測容量は元ファイル全体464KB、`observation`テーブルと索引1,552KB、`weather`スキーマ全体2,072KB、DB全体約21MB。
- 次は日照時間、気圧、湿度、風、積雪、天気概況を追加できるよう項目台帳とCSV解析を一般化し、その後に静岡空港・高根山の台帳を追加する。

## 1. 対象範囲

最初は気象台・観測所の公開観測実績を対象とする。公開されているアメダス観測実績も含む。ナウキャストは別の格子データ製品として後から追加し、初期の収集を遅らせない。

全国・可能な限り長期間の収集を最終的な方向とする。ただし「可能な限り」は、公開範囲、利用条件、配信負荷、費用、自宅サーバー容量に収まる範囲を意味する。全項目が全地点・全年代でそろうとは仮定しない。

## 2A. 藤枝市稲川のサンプル設計（v0.2で追加）

ユーザー指定の４候補を以下のように扱う。気象庁「地域気象観測所一覧」の資料時点は2026-03-24、確認日は2026-09-12。機器が測る内容と、この取得経路で公表される項目は区別し、CSV上の提供可否は期間別に確認する。

| 候補 | 公式一覧で確認できる主な項目 | 検証上の役割 |
|---|---|---|
| 静岡（静岡地方気象台、50331） | 気温・降水量・風向風速・日照・湿度・気圧等 | 最初の１地点取込候補。項目の多い地点を基準にする |
| 静岡空港（50477） | 気温・降水量・風向風速。一覧では日照・湿度・気圧を除く | 静岡との共通項目の比較、提供対象外の処理 |
| 高根山（50317、藤枝市瀬戸谷） | 降水量のみ。標高415m | 雨量だけの観測所と、地形差のある地点の比較 |
| 島田 | 現行一覧に記載を確認できず。過去データ検索には掲載 | 観測期間・旧項目の確認、観測終了後を取得失敗にしない検証 |

出典：[気象庁・地域気象観測所一覧](https://www.jma.go.jp/jma/kishou/know/amedas/ame_master.pdf)、[島田の過去データ検索](https://www.data.jma.go.jp/stats/etrn/index.php?prec_no=50&block_no=0452&year=&month=&day=&view=)

C1は静岡の日別値１か月から始める。C2では静岡空港・高根山を加える。初期必須項目は地点ごとの提供能力に合わせ、高根山に気温を要求しない。島田の直近３年データが存在するとは仮定せず、提供期間を調べて別の歴史データ用期間を選ぶ。終了日や他地点への継承関係は未確認であり、静岡空港と自動接続しない。

比較は雨量を静岡・静岡空港・高根山で、気温・風を静岡と静岡空港で試す。日照・湿度等は比較相手がいない状態を正しく表示する。４候補の全項目が同じ期間にそろうことは完了条件にしない。

農地からの正確な距離・最寄り順位・標高差は、ピン位置確定後に計算する。高根山は標高条件で自動比較候補から外れる可能性があるが、収集対象からは除外せず、手動の参考比較に残す。

## 3. 取得元の確認と優先順位

| データ | 第一候補 | 確認すること |
|---|---|---|
| 過去の日別・時別観測値 | 気象庁「過去の気象データ・ダウンロード」 | 項目、地点ID、期間、CSVオプション、自動取得手順 |
| 最新の補助データ | 気象庁「最新の気象データ」CSV | 対応項目、期間の意味、更新遅延、過去値との対応 |
| 観測所情報 | 気象庁の公式観測所一覧・履歴等 | ID体系、位置、標高、項目、移転・廃止 |
| CSVで補えない項目 | 公式HTMLの表、または別の配布経路 | 取得条件、構造変更検知、代替手段 |
| 農地 | 初期は手動ピン。後続で農水省の筆ポリゴン | 年度、座標系、利用条件、農地情報との対応 |

CSVの公開は確認済みだが、必要な条件を指定した無人取得の実装は未検証。「過去データ」サイトを安定性保証のある公開APIとは扱わない。C0で少量取得を検証し、自動化が成立しなければ手動取得CSVのインポートを先に完成させる。

「最新の気象データ」CSVは、全観測項目の瞬時値を返す万能なAPIではない。日最高値や期間雨量などを通常の時別値と混ぜない。[過去データ](https://www.data.jma.go.jp/risk/obsdl/)、[最新CSVの仕様](https://www.data.jma.go.jp/stats/data/mdrr/docs/csv_dl_readme_new.html)

取得は同時１件、リクエスト間隔２秒、タイムアウト30秒、再試行は最大３回の段階的な待機とする。これは内部設定であり、公式に許容された頻度ではない。配信側の指示や429・503応答に従って待機し、継続失敗時は停止する。不要な再取得はファイルハッシュ・取得履歴で減らす。大量取得は経路・量を再検討する。[気象庁の利用上の注意](https://www.data.jma.go.jp/risk/obsdl/)

## 4. 気象データソースの選択肢と制約

### 4.1 選択肢

| ソース | 空間分解能 | 費用 | 自動化 | 備考 |
|---|---|---|---|---|
| 気象庁アメダス（CSV） | 観測所点 | 無料 | 可 | 現行基盤。日次更新済み |
| 気象庁アメダス（時別） | 観測所点 | 無料 | 可 | BLASTAM系に必要 |
| メッシュ農業気象データ（農研機構直） | 1kmメッシュ | 無償（研究・開発・教育・試用） | 不可 | 新認証によりJupyter Lab経由のみ |
| メッシュ農業気象データ（ビジョンテック） | 1kmメッシュ | 1気象要素/月 3,300円 | 可 | WebAPI |
| メッシュ農業気象データ（WAGRI経由） | 1kmメッシュ | WAGRI利用料 44,000円/月、データ0円 | 可 | ファイルDL・OPeNDAP可 |

農研機構直のルートは2026年2月に新認証へ移行し、Pythonからの取得がJupyter Lab経由に
限定された。自宅サーバーのcronから毎朝取得する運用ができない。過去データを手動で
取得してnetCDFで持ち帰る用途には使える。

ビジョンテック直とWAGRI経由の損益分岐は約13.3要素。必要な5要素
（日平均・最高・最低気温、降水量、日照時間）ではビジョンテック直が有利。

### 4.2 メッシュデータの作られ方

メッシュ農業気象データの過去値は、気象庁の1kmメッシュ気候値に、約20km間隔の観測点
（地上気象観測所とアメダスで約900地点）の日々の観測値から求めた偏差を重ね合わせて
作成される。

```text
1kmの空間パターン ← 気象庁メッシュ平年値（1991-2020の30年平均を地形から推定）
日々の変動        ← 約20km間隔の観測点を内挿したなめらかな偏差場
```

気温についてはこの分解が物理的に妥当である。偏差は20km程度の範囲でほぼ共通であり、
地形・標高・海陸による1kmスケールの差は平年値パターンが保持している。

降水についてはこの前提が成り立たない。日々の偏差は空間的になめらかでないため、
アメダス補間版（APCP）は1kmメッシュの形をしているが、日変動の実解像度は
観測網の間隔のままである。

### 4.3 解析雨量の実態

解析雨量はレーダー観測と全国の雨量計を組み合わせた1kmメッシュの前1時間降水量分布で、
30分ごと（速報版は10分ごと）に作成される。日別値ではない。日積算するには重複窓を
考慮し、正時の値のみを使う必要がある。1kmメッシュ化は2006年以降、
GRIB2形式、有償配信である。

解析雨量ベースの日積算（APCPRA）は2008年以降。日々の変動に1km解像度の情報が入るため
APCPより局地性を拾えるが、次の性質がある。

- 防災上の観点から、雨量計のある格子とその周囲8格子は観測値を下回らないよう処理される。
  このため観測点を含む格子を1とすると周囲は0.8程度になる。1km離れただけで
  系統的に2割低く出る（2006-2009年の検証。その後改良が継続しており、
  現在のバイアスの大きさは未確認）
- レーダー由来のため山間部の地形遮蔽による過小評価が残る
- 降雪の推定は苦手

この性質から、降水を総量の閾値で判定せず、降雨の有無と日数で判定する方針とする（[03_data_analysis.md](03_data_analysis.md)10章）。

APCPRAの平年値が1991-2020年で用意されている一方、実績は2008年以降である。平年値が
APCP系列で作成されている場合、APCPRA実績との比較に系統誤差が乗る。要確認事項とする。

### 4.4 系列の抽象化

判定ロジックが取得元に依存しないよう、参照先を1つのIDで抽象化する。

```text
weather_series_id
  amedas:0631      観測所
  mesh:53394611    1kmメッシュ
  sensor:field_12  圃場設置センサー（将来）
```

L1・L2と判定ルールはこのIDのみを知る。ソースの違いはL0からL1への変換に閉じる。これにより
無料層を観測所、有料層をメッシュとする構成や、特定圃場のみ実測値へ差し替える運用を、
判定ロジックを変更せずに行える。

利用者の記入による降水記録は、性質が異なるため同一系列に混ぜず、別テーブル
（`diary_entry`）に置く（[04_cultivation_state.md](04_cultivation_state.md)10章）。

現時点で本番経路に組み込むのは気象庁アメダスのみとする。メッシュ農業気象データの採用可否は、
[BUSINESS.md](../BUSINESS.md)の確認事項が解決してから判断する。

## 5. 処理の流れ

```text
対象設定・取得台帳を読む
 → 地点×項目×期間の未完了区間を作る
 → 小さく分割して取得
 → 元ファイル・取得条件・ハッシュを保存
 → 内容と列構造を検証
 → 共通形式へ変換して一時領域に投入
 → 件数・キー・単位・品質を検証
 → トランザクションで本登録・変更履歴保存
 → 成功した区間だけ台帳を完了にする
```

HTTP成功でも、中身がエラーページなら登録しない。未知の列・単位・品質コードは隔離して失敗扱いとし、黙って列位置で読み違えない。分割途中の失敗では完了済み区間を保持し、再実行は未完了分から行う。

手動取得したCSVも同じ解析・登録処理を通す。取得と解析を分離し、ネットワークなしで再処理できるようにする。

## 6. DBの論理設計

初期は項目ごとに１行を持つ形式にする。観測所ごとに項目が違っても、テーブル列の追加なしに拡張できる。分析では必要に応じて列形式に変換する。

| テーブル案 | 主な内容 |
|---|---|
| source | 提供者、製品、URL、利用条件の確認日、仕様版 |
| station | 内部ID、名称、公式区分、運用期間 |
| station_source_id | 取得元のIDと内部IDの対応、有効期間 |
| station_version | 位置、標高、有効期間、変更根拠。履歴不明を明示 |
| station_capability | 項目、粒度、利用可能期間、実測・推計の区別 |
| element | 気温平均・最高・最低、降水量等のコード、単位、統計種別、期間の解釈 |
| observation | 観測所、項目、対象期間、値、品質、出典ファイル、取得時刻 |
| observation_revision | 変更前後の値・品質、変更時刻、根拠ファイル |
| source_file | 元ファイルの所在、ハッシュ、取得条件、解析器の版 |
| ingestion_run / ingestion_chunk | 実行・区間ごとの成功失敗、件数、再開情報 |
| dataset_revision | データ更新の版、変更した観測所・項目・期間 |

観測値の一意キーは原則「取得元製品＋観測所ID＋項目コード＋粒度＋対象期間開始・終了」。同じ取得を繰り返しても行を増やさず、値や品質が変わった場合だけ改訂履歴を残す。出典ファイルIDは一意キーに含めない。

複数製品に同じ観測値がある場合は出典付きで保持し、分析用の正規化ビューで優先順位を選ぶ。初期は過去データ製品を主として、最新値の補完は対応確認後に追加する。同じ観測所を名称だけで突き合わせない。

農地・作業記録・分析結果は後続編が管理する。前半では観測所の位置と近隣検索の接点を用意する。

## 7. 時刻・品質・地理情報の共通ルール

### 時刻と統計の意味

- 瞬間を表す時刻はタイムゾーン付きで保存し、内部の標準はUTC、画面はJSTとする。
- 日別値には提供元の「対象日」を別に保存する。日別の期間境界は製品の定義に従い、単なる24個の時別値の集計と同一視しない。
- 期間値には開始・終了、期間の長さ、合計・平均・最大等の意味を保持する。24時表記を含む変換をサンプルで検証する。
- 降水量mmと降水強度mm/hを別の項目として扱う。重なりのある累積雨量を足し合わせない。

### 品質

- 数値と品質は項目単位で保存。NULLをゼロに変換しない。
- 「元データで欠測」「その地点では未観測」「公開待ち」「取得失敗」「未取得」を区別する。
- 公式の品質コードと内部で見つけた疑いを別々に保持する。
- 実測、提供元の推計、自前の計算値を区別し、同じ値として上書きしない。
- CSVの均質番号は取得ファイル内での情報として保存する。取得期間が異なるファイル間で同じ番号を同一環境とみなさない。比較可否は別途、履歴と根拠から判断する。

CSVの品質情報・現象なし情報・均質番号、および番号の取得条件依存は公式仕様に基づく。[CSV形式の解説](https://www.data.jma.go.jp/risk/obsdl/top/help3)

### 地理情報

観測所と農地ピンはWGS84のPointを基本とする。距離はPostGISのgeography等でメートル単位に計算し、経緯度の度数を距離として使わない。標高不明はNULL。位置履歴が取得できない期間には現在位置を黙って適用せず、不明または暫定であることを返す。

観測所の「ランク」は固定の優劣として保存せず、項目の有無・実測／推計・継続期間・欠測率を持つ。画面用の分類はそこから作る。

## 8. 自宅運用・容量・移行

DBに書く収集用権限、分析用権限、API用権限を分ける。接続情報は文書やコードに埋め込まない。DBポートをそのまま外部公開しない。

初期のバックアップ目標は日次、別の保存先へコピー、保持14世代。暫定の復旧目標は「最大１日分の損失、１日以内の復元」。実機の容量・回線と復元試験で確認する。DBだけでなく、元ファイル、設定、構造変更SQLも復元対象にする。

容量は「地点数×日数×項目数」の行数に、索引・履歴・バックアップを加えて見積もる。１時間粒度では日別より大きく増えるため、C1で実測した１行あたりサイズと取得時間を用いる。ディスク使用率80%を暫定の拡大停止基準とし、全国の大量取得前に再見積もりする。

SupabaseはPostGISをサポートするが、容量、対応拡張、ロール、接続方式は移行時に確認する。元ファイルはDB外の保存先に置き換えられるよう所在を管理する。初期は特定の時系列拡張に依存せず、通常テーブルと索引から始め、分割は実測に基づく。[SupabaseのPostGIS](https://supabase.com/docs/guides/database/extensions/postgis)

### データ量の方針

L1の日別値は全国・30年でも現実的な容量に収まる。L0の詳細な品質・出典・訂正履歴と、
時別値を長期保持する場合に容量が増大する。

- L1は観測所または気象系列×日で1行の横持ちとし、雨量のみの観測所も同じテーブルに置く
- 単位を持つ連続量は実値の10倍の整数とし、日値は`smallint`、累積値は`integer`を基本とする
- `obs_date`で年単位のレンジパーティションを切る
- 追記中心の時系列であるため`obs_date`にはBRINを併用する
- L0の時別値は保持年数を限定する。平年値は公式値を使うため長期の時別は不要
- メッシュデータを扱う場合、全国約40万メッシュを行に展開しない。netCDFのまま
  L0に置き、契約中の圃場が含むメッシュのみL1・L2へ展開する

時別データを保持する唯一の強い理由は、葉いもち感染好適条件（BLASTAM系）である（[03_data_analysis.md](03_data_analysis.md)12章）。
これを採用しない場合、時別データは不要となる。

### Dockerでの構築・運用方針（v0.3）

ユーザーの方針に合わせ、前半・中盤を自宅サーバーのDocker環境で構築する。初期はDocker Composeで以下のサービスを管理する。

| サービス | 役割 | 実行方式 |
|---|---|---|
| db | PostgreSQL＋PostGIS | 常駐。永続ボリュームを使用 |
| collector | Pythonによる取得・整形・DB登録 | 定期または手動の単発ジョブ |
| analyzer | Pythonによる分析・結果登録 | 収集成功後または手動の単発ジョブ |

Compose自体を時刻スケジューラーとは扱わない。ホスト側の起動処理が収集の終了状態を確認し、成功後に分析を起動する。各ジョブはDBの接続準備を確認し、同じ対象の多重起動をロックで防ぐ。分析に失敗しても次回の収集は止めない。

DBデータ、元CSV、バックアップはコンテナの書き込み層に置かず、明示したボリュームまたはホストディレクトリに保存する。ボリュームの永続化とバックアップは別とし、バックアップは別の保存先へ複製する。通常の再作成でデータを失わないことをC3で検証する。

成果物はCompose設定、Python用Dockerfile、依存関係の固定ファイル、秘密情報を含まない設定例、起動・再取得・復元の手順書。実際の秘密情報はリポジトリ外で管理する。イメージとDB拡張の版を固定し、更新はバックアップと互換性確認後に行う。

初期は収集・分析が共通のPythonイメージを使ってもよいが、実行サービス・コマンド・権限は分ける。分析の依存関係が増えたらイメージも分離する。CPU・メモリ・ディスク上限は実機確認後に設定する。DBは内部ネットワークで接続し、インターネットへ直接公開しない。

## 9. 実装順序と完了条件

| 段階 | 作業・成果物 | 完了条件 |
|---|---|---|
| C0 | 取得元・項目・粒度対応表、サーバー環境確認 | 必須項目の少量取得経路と出典が分かる。自動化可否を記録 |
| C1 | １地点１か月の取得・解析・登録、容量測定 | 元CSVとDBが一致。再実行して重複せず、品質が残る |
| C2 | 観測所台帳、近隣２～４地点、過去３年の段階取得 | 地点・項目・期間別の取得状況を説明できる |
| C3 | 定期実行、訂正・失敗・復元対応 | ７日間、各実行の成否が記録され、失敗分の再開と別DBへの復元に成功 |
| C4 | 分析向けビュー・データ辞書 | 中盤から出典・品質付きで読める。対象の不足を判別できる |
| C5 | 地域・期間・時別値への拡大 | 取得負荷・容量の予算内で段階拡大。全国完了は初期版の条件にしない |

必須の検証ケースは、空欄とゼロ、未知の列、日付境界、同じCSVの再登録、訂正値、途中失敗、提供項目なし、バックアップ復元。成功ケースだけでなく、誤った値を登録しないことを確認する。

## 10. 後続拡張の接点

農地は当初手動ピンでよい。筆ポリゴン取得は地域を絞って別ジョブにし、出典・年度・元IDを保持する。[農水省の筆ポリゴン](https://www.maff.go.jp/j/tokei/census/shuraku_data/2025/mb/index.html)

予報には「発表・基準時刻」「対象時刻・期間」「製品」「格子」「抽出方法」が必要なため、observationとは別のテーブルを追加する。ナウキャストの元ファイル保存期間は、製品の容量・契約と目的を確認して決める。農地の抽出値だけ保存しても、元ファイル取得量が同じ割合で減るとは限らない。
