## 最初に読む資料

作業開始時に `docs/plans/README.md`、`docs/plans/01_overall.md` と作業対象の編を読む。全体編とデータ収集編の現時点版はv0.5（2026-09-14）、その他の編はv0.3（2026-09-12）。

- 前半：`docs/plans/02_data_collection.md`
- 中盤：`docs/plans/03_data_analysis.md`
- 後半：`docs/plans/04_application.md`

## 開発・コーディング手法
- ファイルやフォルダの作成、コーディングの記載は開発者が行います。
- AIへの期待は、開発者の支援です。具体的には以下のとおりです。

### AIへの依頼
- まず全体像を把握してください
- その次に、大まかな手順を示した上で、開発方針・開発手順を開発者に確認してください。大枠から入って細部を詰めていく手順が好みです。逆にいうと、細部から入らないでください。
- その次に、必要なファイルやファイルへのコーディング案を示してください。
- これを細かくステップを刻んで進めるようにしてください。
- 複数の選択がある場合は、メリット・デメリットを示した上で開発者に判断を委ねてください。
- この依頼は、迅速で正確な開発とAIとして目指しやすい目標と反することから、時間の経過、思考が深まるにつれ忘れがちですので、何度も思い出すようにしてください。

## ユーザーの方針

- まず気象観測所の実績データ収集から着手する。CSV等の配布データを優先し、不足する場合にBeautifulSoupでHTML解析を検討する。
- 前半・中盤はPython、自宅サーバーのDocker Composeで構築する。
- PostgreSQL＋PostGIS、収集、分析を別サービスとして管理する。DB・元ファイルを永続化し、バックアップを別途設ける。
- 将来のSupabase移行を視野に入れる。
- サンプル農地は静岡県藤枝市稲川。正確なピン位置は未確定。
- 観測所候補は静岡（静岡地方気象台）、静岡空港、高根山、島田。島田は現行の継続観測を仮定せず、過去の提供期間を確認する。
- 日照時間、気圧、湿度、風速・風向、雪国向けの積雪、補助的な天気概況は、可変項目対応後にまとめて収集対象へ追加する。数値・方位・文章を同じ型へ無理に統合しない。
- 後半の画面はFlutterを現時点の採用案とし、PCブラウザとAndroid・iPhoneへ段階対応する。
- ナウキャスト・数時間先予報・農地ポリゴン・IoTは後続拡張とする。

## 実装の原則

- 欠測・未観測・未取得・取得失敗を区別し、欠けた値をゼロにしない。
- 観測値の品質・出典・対象期間・訂正履歴を保持する。
- 異常値候補で元データを削除・上書きしない。
- 近隣観測所の値を農地そのものの実測として表示しない。
- 収集と分析を独立実行できる構成にする。
- 計画中の閾値・取得間隔等は暫定設定。検証済みの精度や配布側の許容基準とは扱わない。
- 秘密情報をコード・文書へ記載しない。
- 仕様を変更した場合は関連する計画書と変更履歴を更新する。
