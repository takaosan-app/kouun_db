# 開発計画書 04：後半・アプリ構築編

版：v0.3／更新日：2026-09-12  
到達目標：PCとスマホから、農地にひも付く気象履歴と作業記録を簡単に確認できる。

## 1. 製品の考え方

農家自身が判断できるように、気象の実績と比較結果を分かりやすく見せる。別会話「気象データの農業活用」で検討した、農地ピン、複数観測所、開花・満開などの基準日、作業記録を反映する。

初期は作物共通の画面を作る。水稲、みかん、イチゴなどを個別に作り込む前に、本人と身近な農家の試用で必要な情報を確認する。観測所の外気データをハウス内の値と混同しない。

## 2. 現時点の採用仕様

| 項目 | 計画上の採用内容 |
|---|---|
| 画面 | Flutter／Dart |
| PC | 最初はブラウザ版。Windows・macOS専用アプリは初期対象外 |
| スマホ | 初期の画面確認はスマホブラウザでも行い、Android・iOSアプリを段階提供 |
| API | Python＋FastAPI、バージョン付きのREST API |
| データ | 自宅PostgreSQL＋PostGIS。クライアントはDBへ直接接続しない |
| 地図 | 別会話の希望に合わせGoogle Mapsを第一候補。対応パッケージ・料金・保存条件はP0で確認 |
| 農地の位置 | ピン１点を必須、ポリゴンは任意の将来拡張 |
| 認証 | 本人のローカル試作後、外部試用前に標準的な認証基盤を選定。独自のパスワード認証は作らない |
| 状態管理 | 画面、APIアクセス、表示状態を分離。具体的なパッケージはP0で確定 |
| 通知 | 初期は画面内の状態表示。プッシュ通知は利用者が選ぶ拡張機能 |
| オフライン | 取得済み内容の閲覧を基本案とする。初期は通信不能時の新規保存を行わない |

FlutterはWeb・iOS・Androidへの展開に対応しているが、地図・位置情報・通知・ファイル操作は各環境で検証する。[Flutter公式](https://docs.flutter.dev/platform-integration/web)、[FastAPI公式](https://fastapi.tiangolo.com/)

サンプル農地は静岡県藤枝市稲川。正確なピンはユーザーが確認する。観測所候補は静岡・静岡空港・高根山と、提供期間確認対象の島田。項目がない場合は「未観測／提供対象外」、期間外は「対象期間外」として、欠測と区別する。

## 3. 最初に完成させる利用の流れ

```text
農地名と位置を登録
 → 必要項目を持つ近隣観測所から、主参照と比較参照を選ぶ
 → 最新の利用可能な観測実績と、７日・30日の集計を見る
 → 過去年や近隣観測所との差を確認
 → 作業メモ・開花日などを登録
 → 基準日からの積算を確認
```

日別データだけの段階では「現在の気温」や「今日の確定雨量」は表示しない。「最新の実績：○月○日」「データ更新：○時」のように、観測対象と更新を区別する。数時間先予報は導入するまで機能対象外として扱う。

## 4. 画面構成

| 画面 | 主な表示・操作 | 初期の完了条件 |
|---|---|---|
| 農地一覧 | 名前、作物、最新対象日、主な集計、更新状態 | 複数農地を切り替えられる |
| 農地登録・編集 | 名前、住所・地番メモ、検索、ピン移動 | 検索できなくても手動で位置を確定可能 |
| 観測所選択 | 距離、項目、実測／推計、欠測率、標高 | 主参照１つ・比較最大５つを選べる |
| 農地ダッシュボード | 気温・雨量・日照等、期間集計、基準日集計 | 出典・対象期間・品質を確認可能 |
| 気象履歴 | 日別グラフ・表、期間変更、前年比較 | 値がない箇所をゼロで描かない |
| 観測所比較 | 複数地点の値、差、異常値候補の理由 | 農地の実測と誤解しない表示 |
| 記録 | 作業メモ、作物・品種、播種・開花・満開・収穫等 | 日付の登録・修正・削除ができる |
| 設定 | 参照地点、基準日、単位・表示、アクセス設定 | 変更後に関連集計が更新される |
| 管理画面 | 収集状況、最終成功、失敗区間 | 管理者だけが閲覧できる |

住所・地番から必ず位置が得られるとは仮定しない。検索結果をユーザーが地図上で確認し、修正したピンを保存する。所在地が不明なまま自動確定しない。

最寄り観測所が雨量のみの場合は、気温に別の観測所を指定できる。項目ごとの出典を明示し、複数観測所の値を１地点の実測のように合成しない。履歴上の参照変更は有効日付きで管理する。

## 5. PC・スマホの操作設計

PCでは農地一覧と詳細を並べ、表や比較を見やすくする。スマホでは１画面１目的を基本にし、農地一覧→詳細→記録の短い動線にする。スマホの画面を単に横に引き伸ばしたPC版にはしない。

文字の拡大、十分な操作領域、色だけに頼らない品質表示を採用する。グラフには値を読める表または詳細を付ける。単位と期間を常に表示する。

開花日は本人が入力し、ワンタップの「今日、開花を確認」と後からの日付修正を用意する。未入力でも他の機能は利用できる。基準日を変更した場合は「再計算中」を示し、以前の結果を新しい日付の結果として見せない。

通信不能時は最終取得時刻を明示してキャッシュを表示する。保存に失敗した作業メモを「保存済み」にしない。端末への一時下書きと再送を追加する場合は、重複・競合処理を別途設計する。

前半・中盤は自宅サーバーのDocker Compose上で動作する。APIも同じサーバーに置く場合は独立したサービスとして追加するが、外部公開先はP0で検討する。Flutterの画面やスマホアプリ自体を自宅サーバー内で実行する意味ではない。

## 6. APIとデータの境界

APIは画面に必要な範囲だけ返す。初期の例は次の通りで、実装前にリクエスト・レスポンスをOpenAPIで定義する。

| API案 | 用途 |
|---|---|
| `GET/POST /api/v1/fields` | 自分がアクセス可能な農地一覧・登録 |
| `GET/PATCH /api/v1/fields/{id}` | 農地の詳細・変更 |
| `GET /api/v1/stations` | 座標・半径・項目で観測所候補を検索 |
| `GET /api/v1/observations` | 観測所・項目・期間で観測実績を取得 |
| `GET /api/v1/fields/{id}/metrics` | 期間・基準日集計と比較結果 |
| `GET/POST/PATCH/DELETE .../events` | 作業メモ・基準日イベントの管理 |
| `GET /api/v1/admin/ingestion-status` | 管理者向け収集状況 |

対象期間・件数に上限を設け、大量取得は分割または非同期処理にする。分析中・データ不足・提供対象外を区別して返す。

数値には単位、対象期間、観測所、実測／推計、品質、データ版、計算版を添える。未来の予測値には発表時刻を追加する。欠けた値はnullと理由で返し、架空の値で画面を埋めない。

## 7. アプリ側のデータモデル

| データ | 主な内容 |
|---|---|
| field | 農地名、所有ユーザー、位置、住所・地番メモ、任意の形状 |
| field_station | 項目別の主・比較観測所、参照の有効期間、選定方法 |
| crop_season | 作物・品種、年・作期。複数年栽培にも対応できる識別子 |
| field_event | 作業・開花等の種別、対象日、メモ、作成・更新者 |
| baseline_setting | 積算の基準イベント、任意の基準温度、設定版 |
| field_member | 将来の共有先と閲覧・編集権限。共有機能追加時に実装 |
| attachment | 写真などの保存先。写真機能追加時に実装 |

初期は農地所有ユーザーを必ず持たせる。写真、収量・品質、貸借に伴うデータ引継ぎは拡張とし、誰の記録を誰が引き継げるかを明確にしてから実装する。

## 8. 公開・認証・運用

本人利用のローカル試作と、外部農家への試用を分ける。外部試用前にHTTPS、認証、農地単位のアクセス制御、バックアップ、障害時の連絡方法を整える。農地の詳細位置や作業メモは初期状態で非公開とする。

ユーザーIDをクライアントの入力だけで信用せず、APIで認証済みユーザーと所有権を確認する。２ユーザーのテストで他者の農地IDを指定しても読み書きできないことを確認する。

最初の外部提供先は保留。自宅サーバーの回線・可用性・公開方法を評価し、必要ならAPIやDBを移す。Supabase移行時も画面は同じAPIを使える構成を基本とし、認証IDとの対応を管理する。地図のキーはプラットフォーム・接続元に適した制限を設定する。

## 9. 後続機能

| 拡張 | 追加する価値 | 着手条件 |
|---|---|---|
| 時別実績 | 日中の気温・風等を詳しく見る | 前半の時別値対応と品質検証 |
| ナウキャスト | 直近の雨の動きを表示 | 画像／数値の目的、取得経路、費用・利用条件が確定 |
| 数時間先降水予報 | 作業前後の雨を参照 | 対応する別の予報製品を選定し、発表時刻別に保存 |
| 予報精度の比較 | 地域ごとの予報と実績の違い | 同じ期間・空間を対応付ける評価データがある |
| 写真・収量・品質 | 気象と作業・結果を振り返る | 現場で必要と確認される |
| 通知 | 利用者が指定した条件を知らせる | データの遅延・品質・誤検出を評価済み |
| 筆ポリゴン・土壌・地形 | 地図上の比較・農地管理 | 配布条件・出典・座標系を確認 |
| IoT | ハウス内などの現地実測 | 機器・回線・電源・校正・途絶時の運用を別途設計 |
| JA等の管理画面 | 複数農家の共有・支援 | 本人の共有同意、役割、保守体制を定義 |
| 課金 | 継続運用の費用回収 | 利用実績、コスト、提供範囲を確認して価格を決定 |

ナウキャストと降水短時間予報は別製品として扱う。後者を含む将来の予報機能は、前半の観測実績だけでは実現しない。[気象庁の製品解説](https://www.data.jma.go.jp/developer/weatherdataguide/appendix/2-1-b.html)

## 10. 開発段階・完了条件

| 段階 | 作業 | 完了条件 |
|---|---|---|
| P0 | PC・スマホの画面案、地図試作、API定義 | ピン選択とグラフを両画面で確認。地図条件と認証方針を確定 |
| P1 | 農地・観測所選択、気象履歴の閲覧 | 実データを出典・品質付きで表示 |
| P2 | 比較、作業メモ、基準日集計 | 登録・修正が保存され、再計算に反映 |
| P3 | 認証・公開準備、Android・iOS実機検証 | 他者データへのアクセスを拒否し、基本操作が全対象で成功 |
| P4 | 少人数の試用と改善 | 農地登録、実績確認、メモ、基準日変更の４操作を試用者が完了 |

正式なストア一般公開は初期試用とは分ける。まずPC・スマホで使える試用版を完成させ、利用者の端末に合わせて配布方法を選ぶ。OS最小バージョンは実装時のFlutter対応と試用端末から決める。

必須のテストは、データなし・古いデータ・欠測・分析中の表示、基準日修正、通信失敗、認証切れ、他ユーザーのID指定、PC／スマホでの同じ集計値、地図の手動位置修正。実機確認対象にはPCブラウザ、Android、iPhoneを含める。
