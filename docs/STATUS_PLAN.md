## 2. 完了したこと

### 2.1 L0：収集・原本・詳細DB

- 気象庁の観測地域60件と全国の観測所台帳を取得できる
- 地域、観測所タイプ、月単位で日別観測値を収集できる
- 観測能力コードごとに観測所を分け、共通して取得可能な項目を要求する
- 雨量だけの観測所、積雪を持つ観測所など、観測能力の違いを扱える
- 可変CSVレイアウト、文字観測値、微量降水、欠測を扱える
- 原本ファイル、メタデータ、ハッシュ、取込履歴、訂正履歴を保持する
- 同じ原本と観測値を再取込しても重複しない
- 複数観測所の取得失敗時は観測所単位へフォールバックする
- 収集上の問題を `weather.collection_issue` に記録し、Viewerで確認できる
- 気象庁公式の1991-2020平年値を取得・取込済み
- 気象庁へのリクエスト間隔は2秒を基本とする

### 2.2 L1：軽量日次データ

- `analysis.weather_area`：観測地域
- `analysis.weather_station`：軽量な観測所台帳
- `analysis.weather_station_area`：観測所と地域の多対多関係
- `analysis.weather_element`：L1で扱う気象要素
- `analysis.station_element_capability`：観測所ごとの観測能力
- `analysis.station_daily_weather`：観測所×日付の横持ち日次値
- `analysis.climate_normal_release`：公式平年値の版と適用期間
- `analysis.station_daily_weather_normal`：観測所×月日の日別平年値

連続量は原則として実値の10倍整数で保存する。欠測は `NULL`、微量降水は
`rain_observed` で0.0mmと区別する。詳細な品質はL0へ残し、L1では品質マスクへ圧縮する。

確認済みの台帳件数は次のとおり。

|---|---:|

| L1観測所 | 1,286 |
| 観測所・地域関係 | 1,287 |
| 観測所・要素能力 | 14,541 |
| L1日別平年値 | 457,081 |

L1カタログと平年値の同期は再実行時に変更件数0となることを確認した。

### 2.3 L2：汎用日次派生指標

`analysis.station_daily_weather_feature` に、次を観測所×日付で保持する。

- 平均・最高・最低気温、降水量、日照時間、湿度、風速の累積値
- 各項目の有効観測日数
- 気温、降水量、日照時間の公式平年値との差の累積
- 平年比較に利用できた日数
- 降雨日数と、1mm・5mm・10mm以上の降水日数
- 30℃・35℃以上の最高気温日数
- 25℃以上・0℃未満の最低気温日数
- 1時間・3時間未満の日照日数
- 降雨、無降雨、高温、低温、日照不足の連続日数
- 計算ルールのバージョン

|---|---:|

- 累積降雨日数

- 適用した平年値リリース

- 降水量・日照時間の累積平年差
- 各項目の平年比較有効日数

### 2.4 日次自動運用

systemdの `kouun-db-daily.timer` で毎日09:00 JSTを基準に起動する。
最大10分のランダム遅延を設け、直近7日を再取得・再計算する。

```text
気象庁データ収集
  → L1カタログ同期
  → L1日次データ更新
  → L2日次派生指標更新
```

- 収集：`collector.batch_jma_daily`
- L1・L2：`analyzer.build_daily_layers`
- 収集が失敗した場合は分析処理へ進まない
- L1・L2の更新は同一トランザクションとし、途中失敗時はまとめてロールバックする
- 停止日があっても直近7日の再処理で回復できる

### 2.5 Viewerと運用補助

- 地域を選択してから観測所を選べる
- 観測所を地域コード順で表示できる
- 観測値と公式平年値を表示できる
- 観測値検索用インデックスにより実用的な応答速度を確認した
- 収集エラーを一覧表示できる
- PostgreSQLとViewerはDockerの再起動ポリシーで復旧する

## 3. 決定済みの運用・配置方針

- 自宅サーバーには全期間・全国のL0・L1・L2を保持する
- アプリの初期版は静岡県と接する4県（神奈川・山梨・長野・愛知）に限定する。同期する観測所も同じ5県120件に絞る
- アプリ向けDBにはL1を直近18か月、L2を直近11年（lookback最長10年＋当年）で同期する
- 配信量は「観測所数 × 年数」で決まる。5県120観測所・11年で約134MBの見込み
- 公式平年値はアプリ向けDBにも配置する
- 利用者、圃場、栽培案件、日誌、L3結果はアプリ向けDBへ置く
- 日誌画像はDBへ格納せずCloudflare R2へ置き、DBにはオブジェクトキー等を保存する
- 古い気象データが必要な分析は自宅サーバー側で行い、必要な結果だけを配信する

### 4.2 L3の最小DB設計

最初の対象作物は、いちご（高設栽培）と水稲とする。コードへ作物や状態を直書きせず、
DBのマスターとイベント履歴を中心に設計する。

最小範囲は次のとおり。

- 利用者と圃場（農場の階層は設けない）
- 品目・品種
- 栽培案件（圃場×作期×品目・品種）
- 栽培イベント種別
- 栽培イベント履歴
- 実績イベントから導出した現在状態
- 日誌、農家による降雨確認、病害虫確認、作業記録
- 推定状態と利用者確認済み状態の区別

詳細な状態遷移は[plans/04_cultivation_state.md](plans/04_cultivation_state.md)、
テーブル構成は[plans/07_database.md](plans/07_database.md)に従う。

### 4.3 リスクルールをDB管理

- 閾値、判定期間、重み
- リスク段階と表示文

最初は病害虫の診断ではなく、「注意条件が重なっている」ことを説明する参考情報とする。

### 4.4 アプリ向け配信基盤

- 自宅DBからL1（直近18か月）とL2（直近11年）を同期する方式を決める
- 同期の冪等性、削除、訂正、再送、監視を設計する
- Supabase等のDB容量とegressを実測する
- 認証、組織・利用者・圃場の権限、RLSを設計する
- 圃場ごとに要素別の参照観測所を選べるようにする（降水量は3地点、気温・日照は1地点）

- 日誌画像をCloudflare R2へ保存する
